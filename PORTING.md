# PORTING.md

This is the only document in this repo allowed to name the app this template was extracted from: **Steadily** (internal codename **Gaja**), a child-development app for parents. Every other doc in this repo says "the source app" instead — if you're looking for exact source-repo file paths for anything below, this is the doc that has them.

This file has three jobs: (a) list every subsystem deliberately left out of v1 and how to bring it in later, (b) record every place this template's code intentionally diverges from the source app's equivalent file, and (c) describe the loop for keeping `GOLDEN-FIXES.md` current as new apps built from this template find new bugs.

---

## (a) Subsystems deliberately excluded from v1

Each of these exists, working, in the source app, and was cut from this template to keep v1 slim — not because it's unimportant. Port it in when your app actually needs it.

## (b) Intentional divergences from the source app

These are seams that were deliberately *cut differently* in this template — not omissions, but a different design at the same point in the architecture. If you're porting a fix from the source app and it touches one of these files, expect the shapes to differ.

- **`apps/mobile/src/api/client.ts` — injected auth/paywall hooks instead of hard dependencies.** The source app's client hard-`require()`s RevenueCat for gating-error handling and calls Supabase's `refreshSession()` directly for 401 handling. This template's `client.ts` has zero dependency on either: `configureAuthHandlers({ refreshToken, onUnauthorized })` and `setOnForbiddenHandler(fn)` are called once at app start (by the auth store and the subscription kit respectively) to wire in that behavior. If your app swaps auth providers, you only touch the handler you register, not `client.ts` itself.

  Also note the gating trigger itself doesn't map to one HTTP status: the API returns `PAYWALL_REQUIRED` as **402** and `USAGE_LIMIT_EXCEEDED` as **429** (other 403s exist for non-gating authorization failures), so the response interceptor branches on the **envelope's `error.code`** for any of `402`/`403`/`429`, not on status code alone — a non-gating `429` (e.g. `RATE_LIMITED`) is left alone and annotated with retry-after metadata instead of triggering the paywall handler. If you add a new gated action, give it one of the two gating codes and the existing interceptor picks it up automatically — no client-side wiring per feature.

- **`apps/mobile/src/lib/pushNotification.ts` — registration and routing logically split, in one file.** The source app fuses push-token registration with a ~40-case product route map in one file. This template keeps registration (permissions, channels, Expo token, device upsert) generic and takes an **injected** `NotificationRouteMap` for routing (`resolveNotificationHref(data, routeMap)`, `useNotificationObserver(routeMap)`) — the template ships no product routes at all; you pass your own map.

- **API env schema split into `env.core.ts` + `app.env.ts`, merged by `env.ts`.** The source app has one large Zod schema mixing framework-level vars with ~10 hardcoded product defaults (RevenueCat project id, PostHog project id, etc.). This template splits a generic `coreEnvSchema` (framework vars: Supabase, Vertex, Sentry, PostHog, job auth, email, RevenueCat *shape* but placeholder defaults) from an intentionally near-empty `appEnvSchema` in `app.env.ts` that you extend per app; `env.ts` merges them with `coreEnvSchema.extend(appEnvSchema.shape)`.

- **LLM provider split into `llmProvider.ts` (generic) + `app.llmConfigs.ts` (per-app).** The source app has one `llmConfig.ts` mixing the Vertex/model-registry setup with ~40 product-specific named model bundles. This template's `llmProvider.ts` keeps only the generic tier factories (`flashLiteModel`, `flashModel`, `proModel`, `embeddingModel`) and the `LlmCallConfig` shape; `app.llmConfigs.ts` holds your app's own named bundles (currently two examples: `widgetDescriptionConfig`, `widgetSummaryConfig`).

- **`@steadily-nanny/shared-types` split into generic-only.** The source app's equivalent package mixes generic types (`ErrorCode`, response envelopes, locale) with product constants (a large entitlement/tier map, onboarding step definitions specific to that app's flow). This template's `packages/shared-types` keeps only the generic shapes — `ENTITLEMENT_TIER_MAP` and `ONBOARDING_STEPS` are still real, working structures here, just seeded with one placeholder entry/flow each instead of the source app's full product set.

- **Error codes flattened to 10 generic, HTTP-facing codes instead of ~65 domain-specific ones.** The source app's `ErrorCode` type is a single flat enum with roughly 65 values, many domain-specific (e.g. a "memory not found" code, a "child not found" code) living directly in the same type as generic ones. This template's `packages/shared-types/src/errorCodes.ts` keeps only the 10 generic, client-branchable codes (`VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMITED`, `INTERNAL_ERROR`, `EXTERNAL_SERVICE_ERROR`, `PAYWALL_REQUIRED`, `USAGE_LIMIT_EXCEEDED`). Domain-specific detail doesn't get its own code here — it rides in `BaseError`'s `metadata` field, or in a named subclass (e.g. a `WidgetNotFoundError extends NotFoundError`), while the wire-level `code` stays one of the 10 generic values. Note: there is **no** secondary "reason metadata" mapping layer beyond this — if you were expecting a two-tier product-code-to-generic-code translation design, that's not what either the source app or this template actually implement; this flatten-to-10 approach is the real, simpler design.

- **Resource-ownership middleware generalized from "child ownership" to any resource.** The source app's ownership-check middleware is hardcoded to the concept of a child (`validateChildOwnership`, checking a `childId` param against a parent-child relationship table). This template's `apps/api/src/middlewares/validateResourceOwnership.ts` exports `makeOwnershipValidator<T>(options)`, taking a `param` name and a `lookup(userId, resourceId): Promise<T>` function — the widget domain's `widgetRoutes.ts` is the worked example (`authWithOwnership(WidgetIdParamSchema, { param: 'widgetId', lookup: widgetQueryService.getOwned })`). Preserves the same positive/negative-cache TTL behavior as the source app's version.

- **Device registration moved to `POST /api/v1/notifications/devices`.** The source app registers devices as part of a broader user-profile update flow. This template exposes it as its own endpoint (`apps/api/src/domains/notification/routes/notificationsRoutes.ts`, called from the mobile side via `notificationsApi.registerDevice` in `apps/mobile/src/api/endpoints/notifications.ts`), called explicitly after profile creation succeeds (see `GOLDEN-FIXES.md` #7) rather than folded into a profile-update side effect.

- **Wire-schema promotion pattern: define the contract in `shared-types` first, not domain-local.** `docs/templates/shared/widget.schema.ts` and the real `packages/shared-types/src/schemas/widget.schema.ts` both demonstrate the pattern for a new feature: define the Zod request/response schemas once in `packages/shared-types/src/schemas/<feature>.schema.ts` so the API validates requests against them and the mobile app validates responses against the *same* import — never redefine the shape in both apps. The widget example now follows this end-to-end: `apps/api/src/domains/widget/schemas.ts` is a thin re-export barrel over the shared module (keeping domain-internal `../schemas` imports stable while any server-only schemas would stay local), and `apps/mobile/src/api/endpoints/widgets.ts` imports the same `WidgetSchema`. The shared `WidgetSchema` is intentionally stricter than a hand-rolled local copy would be (`z.uuid()` ids, `.min(1)` name), so mobile response validation is tighter — by design, not a regression.

- **No subscription-sync endpoint — webhook + `GET status` only.** The source app has additional sync/reconciliation surface beyond the webhook. This template's `apps/api/src/domains/subscription/routes/subscriptionRoutes.ts` exposes only `GET /status` and `GET /usage` (both read-only, `requireAuth`) — all subscription **writes** happen exclusively via the RevenueCat webhook (`POST /api/webhooks/revenuecat`) and the atomic RPCs in `supabase/migrations/006_subscriptions_usage_email.sql`. If you find yourself wanting a client-triggered "sync my subscription now" endpoint, that's the RC reconciliation cron subsystem (see table above), not a gap in this endpoint.

## (c) The back-port loop

This template has no proactive sync back to the source app, and the source app is permanently read-only with respect to this project — nothing here ever gets pushed back into it. Instead:

1. While building an app from this template, when you fix a real production bug (not a one-off typo) — especially anything that took real time to diagnose — add an entry to `GOLDEN-FIXES.md` in **this** template repo, in the same session you fix it, using the same Symptom → Root cause → Where it lives → What not to do shape as the existing entries.
2. If the fix touches a file listed in section (b) above, note whether the divergence still makes sense or whether the new bug reveals the seam was cut wrong — if several apps hit the same problem with a diverged file, that's a signal to reconsider the divergence, not just patch around it.
3. Code back-ports between sibling apps built from this template are manual and optional — `GOLDEN-FIXES.md` is the thing that actually needs to remain current; a stale golden-fixes doc that lets a known bug get rediscovered is treated as a documentation defect, same severity as a code defect.
