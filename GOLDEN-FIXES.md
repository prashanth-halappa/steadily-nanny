# GOLDEN-FIXES.md

This is the highest-value doc in this repo — it survives even if the template's code eventually rots. Every entry below is a production bug that was expensive to find, with the fix preserved so nobody re-discovers it the hard way. When a new golden fix is found in an app built from this template, append it here (see the back-port loop in `PORTING.md`).

Format: **Symptom → Root cause → Where the fix lives in this repo → What not to do.**

## Shipped in this template

### Mobile

**1. Paywall crash on first launch after env drift (App Store Guideline 2.1(a))**
- **Symptom:** the app crashes hard (native, not a JS error) the instant a paywall screen opens, on both iPhone and iPad.
- **Root cause:** on iOS, any RevenueCat `Purchases.*` call — including read-only ones like `getOfferings()` — made before `Purchases.configure()` triggers a Swift `fatalError`, which is a native process abort that no surrounding JS `try/catch` can intercept. If the app ships without a valid RC key (env misconfiguration), `configure()` silently no-ops and the first paywall path becomes an unrecoverable crash.
- **Where the fix lives:** `apps/mobile/src/domains/subscription/utils/paywallReadiness.ts` — `isPaywallReady(context)` checks `useSubscriptionStore.getState().isConfigured` and reports to Sentry (tagged with the caller) before returning `false` instead of letting the call through.
- **What not to do:** never call into the RevenueCat SDK (`Purchases.*`, or any store wrapper around it) without calling `isPaywallReady()` first at every paywall entry point. Don't assume `configure()` succeeded just because the app didn't throw a JS error.

**2. NativeWind `className` silently fails on Reanimated `Animated.View`**
- **Symptom:** an animated element visually overflows its parent, or its Tailwind classes (color, background) don't apply reliably, and `overflow-hidden` on the parent does nothing to clip it.
- **Root cause:** NativeWind's `className` prop and Reanimated's `Animated.View` don't compose reliably — the animated style and the class-derived style can race, and clipping behavior breaks.
- **Where the fix lives:** the convention (never `className` on an `Animated.View`; use inline `style={{}}` or `useThemeColors()` for dynamic colors) plus the escape-hatch hook itself: `apps/mobile/lib/design-tokens/useThemeColors.ts`. The canonical, heavily-commented reference implementation is `apps/mobile/src/components/ui/loading-indicator.tsx`; see also `apps/mobile/src/components/ui/progress.tsx`, `apps/mobile/src/components/ui/loading-button.tsx`, and `apps/mobile/lib/animations/StaggeredFadeIn.tsx` for more worked examples.
- **What not to do:** don't put layout/color `className` directly on an `Animated.View` — split it into an inner static `View` for `className` and keep only the animated `style` on the `Animated.View`. There is no automated Biome/CI guard for this in the template (it's convention + comments only) — if you want one, this is a good candidate for a custom lint rule.

**3. Numeric `fontWeight` needs a VARIABLE font, not per-weight static files (Daylight; Sora removed, Figtree Variable shipped)**
- **Symptom (historical):** with Sora, setting a numeric `fontWeight` (e.g. `700`) did nothing on iOS, or produced synthetic ("faux") bold — each weight was a separate font file and iOS only picked the right glyphs via `fontFamily: 'Sora-*'`, not `fontWeight`.
- **Root cause / fix:** the bug is per-weight **static** font files, not custom fonts in general. Daylight now ships **Figtree Variable** (`apps/mobile/assets/fonts/Figtree.ttf`) — a single file with a continuous `wght` axis (300–900) — registered via the `expo-font` config plugin in `apps/mobile/app.config.js`. Numeric `fontWeight` (and Tailwind `font-medium` / `font-semibold` / etc.) keeps working because iOS interpolates along that axis instead of switching font files.
- **The naming trap:** this font's name table has nameID 1 (Family) = `"Figtree Light"` and nameID 6 (PostScript) = `"Figtree-Light"`, because its default named instance is the Light weight — but nameID 16 (Typographic Family) = `"Figtree"` is the one spanning all 7 weight instances. **Use `fontFamily: 'Figtree'`.** Using `'Figtree Light'` or `'Figtree-Light'` resolves straight to the Light face with no family to interpolate across — every numeric `fontWeight` then silently renders Light, with no error. See `apps/mobile/assets/fonts/README.md` for the full name-table breakdown.
- **Where the fix lives:** `apps/mobile/lib/design-tokens/typography.ts` — tokens carry `weight`, the typography factory maps it to `fontWeight`, and `fontFamily: 'Figtree'` is set once there. `apps/mobile/assets/fonts/README.md` documents the naming trap; `apps/mobile/app.config.js`'s `expo-font` plugin entry registers `Figtree.ttf`.
- **What not to do:** don't reintroduce per-weight **static** font files (`Figtree-Bold.ttf`, etc.) — that's the original bug. Don't set `fontFamily` to `'Figtree Light'` or `'Figtree-Light'` — that's the naming trap, and it fails silently.

**4. `Linking.openURL` fails on the app's own universal-link domain**
- **Symptom:** tapping a link to the app's own marketing/terms domain (the same domain claimed for universal links) fails silently or shows "Unable to open URL."
- **Root cause:** because the app claims universal links for that domain, iOS/Android try to route the URL back into the app instead of a browser — and if there's no matching in-app route, the open fails.
- **Where the fix lives:** `apps/mobile/src/utils/openExternalUrl.ts` — routes `http(s)` URLs through `WebBrowser.openBrowserAsync` instead of `Linking.openURL`; non-http schemes (`mailto:`, `tel:`) still use `Linking.openURL`.
- **What not to do:** don't call `Linking.openURL` directly for any `https://` link to your own domain (privacy policy, terms, marketing pages) — always go through `openExternalUrl`.

**5. Sign in with Apple only returns name/email on the FIRST authorization**
- **Symptom:** a returning user who re-authenticates with Apple has no name on their profile, even though they granted it the first time.
- **Root cause:** Apple's privacy model only includes `fullName`/`email` in the authorization credential on the user's very first Sign-In-with-Apple grant for your app; subsequent sign-ins omit them.
- **Where the fix lives:** `apps/mobile/src/store/auth.ts`, `signInWithApple` — captures `fullName`/`email` off the initial `AppleAuthentication` credential (not a token refresh) and writes it via `supabase.auth.updateUser({ data: metadata })`; the store's `onAuthStateChange` handles the resulting `USER_UPDATED` event to keep local state in sync.
- **What not to do:** don't rely on re-requesting Apple sign-in to recover a missing name — it won't come back. Capture and persist it on first grant.

**6. A deleted-but-still-cached user can relaunch into a broken session**
- **Symptom:** a user deleted server-side (e.g. via an admin action or account-deletion request) can still open the app and appear "logged in" until some later API call finally 401s.
- **Root cause:** a persisted Supabase session (JWT) can outlive the backend user record it names; simply trusting a valid-looking cached session doesn't confirm the account still exists.
- **Where the fix lives:** `apps/mobile/src/store/auth.ts` — the `INITIAL_SESSION` handler calls `supabase.auth.getUser()` at launch (not just trusting the cached session), which round-trips to Supabase and surfaces a deleted-user error immediately rather than on whatever API call happens to fire first.
- **What not to do:** don't skip the launch-time `getUser()` call to save a network round-trip — that's exactly the corner case it exists to catch.

**7. Device push-token registration can race ahead of profile creation (FK violation)**
- **Symptom:** device/push-token registration silently fails for new users with a foreign-key violation.
- **Root cause:** if device registration is allowed to fire before the user's profile row exists, its foreign key (see fix below) has nothing to point at yet.
- **Where the fix lives:** two halves — the DB contract in `supabase/migrations/003_user_device_info.sql` (`user_device_info.user_id` references `user_profiles(user_id)`, **not** `auth.users` directly, precisely so this ordering is enforced by the database, not just convention), and the call site in `apps/mobile/src/hooks/mutations/useUpsertProfile.ts`, which calls `registerDeviceWithBackend()` (from `apps/mobile/src/lib/userDevice.ts`, explicitly commented `GOLDEN (FK ordering)`) only after profile creation succeeds — also invoked from `apps/mobile/src/lib/pushNotification.ts`'s registration flows.
- **What not to do:** don't call device registration before the profile-creation mutation has succeeded, and don't change `user_device_info`'s FK target back to `auth.users` — that would silently re-open the race.

**8. Test files matching a route-file naming pattern become real routes in expo-router**
- **Symptom:** a colocated test file named to match a route file (e.g. something like `_layout.test.tsx` sitting next to `_layout.tsx`) gets picked up by expo-router as an actual navigable route.
- **Root cause:** expo-router's file-based routing treats any file inside `src/app/` as a route candidate by filename pattern; a test file that shadows a route name collides with it.
- **Where the fix lives:** the convention this template follows — test files live under `__tests__/` subfolders, never colocated inside `src/app/` with a name that could match a route pattern. See `apps/mobile/src/domains/widget/__tests__/widgetScreens.test.ts` and `apps/mobile/src/app/__tests__/rootLayout.providerOrder.test.ts` for the pattern.
- **What not to do:** don't add a `*.test.ts(x)` file directly inside `src/app/` (or any expo-router route directory) next to the route files it's testing — put it in a `__tests__/` folder instead.

**19. Shadowed surfaces need opaque backgrounds (Daylight uses RN `boxShadow`, not `elevation`)**
- **Symptom:** a card that looks fine on iOS shows an unwanted shadow bleed or muddy tint on Android, because the card's background is translucent.
- **Root cause (historical):** Android's `elevation` prop composites against the view's actual (possibly translucent) background. Daylight avoids `elevation` entirely — shadows come from React Native's multi-layer `boxShadow` style array via `useElevation()` in `apps/mobile/lib/design-tokens/elevation.ts`. That path is less prone to the old bleed, but the discipline still holds: a translucent surface under any shadow reads wrong on device.
- **Where the fix lives:** `apps/mobile/lib/design-tokens/elevation.ts` — `useElevation()` returns `{ card, liveCard, row }` styles derived from the palette. Consumers merge them inline (`style={[elevation.card, style]}`), never via Tailwind `shadow-*` (NativeWind's box-shadow parser is broken and silently drops multi-layer shadows).
- **What not to do:** don't put `shadow-sm` / `shadow-md` / etc. on a component and expect it to work — use `useElevation()`. Don't combine elevation styles with translucent `bg-card/90` (or any tinted overlay) on the same surface; use opaque `bg-card` on shadowed cards.

**30. `bun run format` DELETES an effect dependency the body never reads — a state flag used only as a re-render trigger is silently removed, and the retry it powers stops working**
- **Symptom:** a "try again" button does nothing. Pressing it flips the state it is supposed to flip, React re-renders, and the effect that should re-run the work never fires again. No error, no lint warning, no failing typecheck — and the code reads correctly, because the dependency is still sitting in the array where the author put it. Then, at some later commit, it isn't.
- **Root cause:** `bun run format` is `biome check --write --unsafe . && biome format --write .` (root `package.json:15`, mirrored in both apps). The `--unsafe` pass applies fix-safety-`unsafe` fixes for **warn**-level rules, and `correctness/useExhaustiveDependencies` is one of them: it removes an "extra" dependency — a value listed in the array that the effect body never reads. A flag whose entire job is *to be a re-render trigger* is, by construction, never read in the body, so it looks exactly like an extra dependency and gets deleted. Two things make this hard to see coming. The rule is **not configured in `biome.json` at all** — it is inherited from `"recommended": true` (`biome.json:31`), so grepping the config tells you nothing. And the deletion happens in the **quality gate's own format step**, after the author has finished and after the reviewer has read the diff: `bun run qc` verifies formatting and goes red on drift, so the next person runs `bun run format`, and *that* is the commit where the retry breaks.
- **Where the fix lives:** read the flag in the effect body, so it is a genuine dependency rather than an extra one. `apps/mobile/src/domains/setup/components/ChildrenScreen.tsx:66` — `if (bootstrapFailed) return;`, guarded by a comment (`:60-65`) explaining that the early return is load-bearing twice over: it makes the dependency real, and it deliberately holds the retry while the error screen is up. The flag is still in the array at `:118`; `retryBootstrap` (`:129-132`) clears it and the ref together. Pinned by `it('re-attempts the bootstrap when the retry affordance is pressed')` and `it('shows a retry affordance when household bootstrap fails, instead of spinning forever')` (`ChildrenScreen.behavior.test.tsx`). It bit this repo once and the test run — not the review — is what caught it.
- **What not to do:** don't put a value in a dependency array that the effect body does not read, and don't "fix" the resulting breakage by adding a `biome-ignore` or turning the rule off — both leave the next reader with an effect whose dependency array lies about what it depends on. If you genuinely need a re-render-only trigger, read it (even as a guard that returns early) so the rule and the runtime agree. And don't assume `bun run qc` being green before you format means it will be green after: `qc` is read-only by design (`docs/DEFECT-LOG.md` D52), so `format` is the only step that rewrites code, and it rewrites it *after* the last thing anyone looked at.

**34. A `'widget'`-directive body is serialized SOURCE, evaluated in a bare JavaScriptCore context — any identifier borrowed from module scope typechecks, lints, and compiles clean, then throws at render, only inside the extension**
- **Symptom:** the TodaysCover widget threw `ReferenceError: Can't find variable: STALE_MS` on render — in both `systemSmall` and `systemMedium` families, reproduced from widget-gallery preview and confirmed identical to what WidgetKit renders on a real home screen (`docs/screenshots/widgetsandla/INDEX.md` defect 1). `bun run qc` was green: the file typechecks (the identifier is a real, correctly-typed import) and lints clean.
- **Root cause:** `babel-preset-expo`'s widgets-plugin replaces a function carrying the `'widget'` directive with a STRING of its own source; `WidgetsJSRuntime.swift` evaluates that string in a bare JavaScriptCore context inside the widget extension, whose only globals are what `expo-widgets`' `bundle/index.ts` installs (the `@expo/ui/swift-ui` views/modifiers and the JSX runtime shims) — module scope does not travel with it. So a body that references a sibling `const`, a helper, or any repo import compiles fine (the identifier legitimately exists in the authoring module) and only fails where it actually runs, which no TypeScript or Biome check can see.
- **Where the fix lives:** every identifier a widget body needs is inlined into the body itself or arrives via props — never referenced from module scope. Pinned by `apps/mobile/src/widgets/__tests__/widgetScope.test.ts`, which brace-counts each of the five widget files' `'widget'` body, collects every module-scope `const`/`let`/`function` declaration and non-`@expo/ui` import, and fails if the body's source text contains any of those names — plus a `FORBIDDEN_CONSTANTS` list (`STALE_MS`, `AS_OF_MS`, `SNAPSHOT_DEGRADE_MS`, `SNAPSHOT_AS_OF_MS`, `RECEIPT_LINGER_MS`, `palette`) that must appear only as inlined figures, never as names. Each widget's own `*.palette.test.ts` keeps its in-body-duplicated palette hexes honest against `palette.dark`. Both checks were confirmed to fail against the pre-fix source before being kept.
- **What not to do:** don't reference a module-level `const`, helper, or repo import (anything other than an `@expo/ui/swift-ui` value) inside a `'widget'`-directive body, even though the file compiles and lints without complaint. And don't trust a rendering test to catch this class of bug — none of these components can render outside WidgetKit, so only a source-text scope check like `widgetScope.test.ts` can.

**35. JS `null` in a widget payload becomes `NSNull`, which `UserDefaults` rejects with a reasonless ObjC exception — and every widget silently receives nothing**
- **Symptom:** `updateSnapshot`/`updateTimeline` calls threw `Exception in HostFunction: <unknown>` and no widget extension ever received real data — no `__expo_widgets_*_timeline` key ever appeared in the App Group at all (`docs/screenshots/widgetsandla/INDEX.md` round-2 note). The debugging trap: the error has no readable message or stack pointing at the offending field, because it's a native ObjC `NSInvalidArgumentException`, not a typed Expo/JS error.
- **Root cause:** `updateTimeline` stores props verbatim via `UserDefaults.set`, and `expo-modules-jsi`'s `JavaScriptValue.getAny()` maps both JS `null` and `undefined` to `NSNull()` on the way across the bridge. `NSNull` is not a property-list type, so the entire write throws — one `null` anywhere in the payload loses the whole update, not just that field.
- **Where the fix lives:** `apps/mobile/src/lib/widgetSnapshot.ts`'s `widgetSafeProps()` (`:807-821`) recursively strips every `null`/`undefined` key/array-item on the way into `expo-widgets`, applied in `applyOne()` (`:759-787`) before every `updateSnapshot`/`updateTimeline` call. The payload builders keep their `| null` fields — `null` is still the honest shape for "computed, and there's nothing there" at the builder layer, and the builder tests assert it — this is deliberately a wire-format fix, not a data-model one. An absent key reads back as `undefined` in the widget's JS runtime, which is why every read in `src/widgets/` already uses `?.`/`??`/truthiness.
- **What not to do:** don't hand a builder's payload straight to `expo-widgets` — always route through `widgetSafeProps` at the wire, and if you add a new widget target, wire its `updateSnapshot`/`updateTimeline` through the same `applyOne` path rather than calling the native API directly. And never compare a widget prop with `=== null` inside a widget body — absent means `undefined` there, not `null`.

**36. Native-module access on any cold-start / pre-login path must be a lazily-guarded, memoized require — a static import turns binary/JS skew into a redbox before a user ever sees a login screen**
- **Symptom:** happened twice, same shape both times — `expo-calendar` (via `calendarSyncNative.ts`) and `expo-widgets` (via `AppBootstrap`'s widget imports). A dev client built before the native pod was linked, or JS shipped ahead of the native build by an OTA update, turned a decorative feature's missing module into a hard crash that took the entire private app area down before login.
- **Root cause:** both packages resolve their native module at *import* time — a top-level constant read directly off it (`ExpoWidgets`'s `widgetsDirectory`, `expo-calendar`'s module binding) — so `Cannot find native module 'X'` fires while the bundle is being evaluated, not on first use. Both modules are reached from `AppBootstrap`/`_layout`, which mounts before authentication, so a static import there fails before a user ever reaches a screen that could work around it.
- **Where the fix lives:** a memoized lazy `require()` behind a function, cached after the first resolution, that returns `null` (never throws) on failure, paired with one-per-call-site failure reporting so nothing downstream needs to know the difference between "never tried" and "unavailable." `apps/mobile/src/lib/expoWidgets.ts`'s `widgets()` (`:58-68`) and `apps/mobile/src/domains/schedule/utils/calendarSyncNative.ts`'s `calendar()` (`:40-49`) are the two instances of the identical pattern; `reportWidgetFailure` (`expoWidgets.ts:43-48`) logs and reports to Sentry once per site via a `Set`, so a poller like `applyWidgetSnapshots` (which runs on every query settle) can't flood the log. Every downstream caller (`applyOne`, `createWidgetSafe`, `createLiveActivitySafe`, `listWritableCalendars`, `requestCalendarPermissions`) already treats a missing module as "do nothing" / "nothing granted" rather than an error to propagate.
- **What not to do:** don't statically import a package that resolves a native module at import time (any Expo config-plugin module, in practice) into a file reachable from `AppBootstrap` or any other pre-login/cold-start path — wrap it in a lazy, memoized, try/catch accessor, and make every caller treat "unavailable" as a legitimate degrade-to-no-op state rather than something to rethrow into React.

**37. Simulator verification traps specific to Live Activities and widgets**
- **Symptom / traps, all hit during the same on-device validation pass (`docs/screenshots/widgetsandla/INDEX.md`):**
  - **Maestro pins to the wrong device whenever two simulators are booted, and `--udid` does NOT save you.** Originally recorded as an MCP-tool defect with the standalone CLI as the workaround. That workaround is WRONG: `maestro --udid <nanny-udid> test flow.yaml` printed `Running on iPhone 17 Pro Max - <nanny-udid>` and then read and tapped the **iPhone 16 Pro's** screen — proven by its own debug screenshot, which came back at 16 Pro resolution showing the parent app. Taps land in another app and report `COMPLETED`; assertions fail against a screen you are not looking at. **The only reliable configuration is exactly one booted simulator** (`xcrun simctl shutdown <other-udid>`); with one booted, the same flows worked first time. `xcrun simctl io <udid> screenshot` remains correct per-device and is how you catch this.
  - **A simulator build made with `CODE_SIGNING_ALLOWED=NO` has no entitlements, so the App Group does not exist and no widget can ever receive a snapshot.** Entitlements are embedded by the ad-hoc "Sign to Run Locally" step that flag suppresses; `codesign -d --entitlements - <app>` then prints nothing. Nothing errors — the app also hangs on its loading gate, because the auth store persists with `secure: true` and the keychain is gone too, which reads exactly like a slow/broken API. Build WITHOUT the flag and confirm with `xcrun simctl get_app_container <udid> com.jetto.steadily.nanny groups` before concluding anything about a widget. (`PROJECT-STATUS.md`'s iOS build section carries the corrected recipe.)
  - **`reportWidgetFailure` logs only the FIRST failure per site** (`apps/mobile/src/lib/expoWidgets.ts` — it throttles so `applyWidgetSnapshots` can't bury the dev server). So "no `la:receipt` in dev.log" does not mean no failure; it can mean the second one. When diagnosing a widget/LA path, add a temporary unthrottled `console.warn` rather than trusting the absence of a report.
  - **This trap manufactures false regressions.** A round-2 validation pass reported the Live Activity receipt as a confirmed regression on a clean account — "zero LA content at +15s and +86s, nothing in dev.log". Re-run with one simulator booted, the receipt rendered correctly ("✓ Clocked out at 7:11 PM / 2m recorded") within the window, and the clock-out was confirmed independently on the parent device. The tell was **"nothing in dev.log"**: if the app under test had really performed the action, its own trace would be there. Silence in the log means the action never reached that device — suspect the harness before the code.
  - **Backgrounding vs. killing the app during a Live Activity test are not interchangeable.** `pressKey: Home` (background) is safe; `simctl terminate` (kill) can race an in-flight mutation's success callback if triggered too early, corrupting the very state you're trying to observe.
  - **`ProgressView(timerInterval:)`'s default label is a ticking seconds timer that `@expo/ui` cannot suppress.** SwiftUI's `init(timerInterval:countsDown:label:)` always shows a live `currentValueLabel` unless you use the four-argument init that replaces it — `@expo/ui` exposes no such prop, and `labelsHidden()` hides a different slot. It shipped a ticking `2:41:50` into the expanded Dynamic Island, overflowing its frame and drawing over the Clock out button (`apps/mobile/src/widgets/OnTheClock.tsx:28-42`). Fix: use a determinate `ProgressView(value:)` (`init(value:total:label:)` has no current-value label at all) and compute the fraction at render.
  - **A prior round's screenshot-staleness note did not reproduce this round** — `xcrun simctl io screenshot` was confirmed reliable and per-device throughout this pass, but the earlier note exists, so don't assume the tool is always fresh; re-verify a suspicious capture against a second screenshot before trusting it as evidence of a bug.
  - **A Live Activity never renders in the Dynamic Island while its own app is foregrounded.** Observed live on the 16 Pro: three clock-ins in a row showed no Island element at all until the app was backgrounded, at which point a long-press revealed the full activity. This is the single most misleading trap of the set — a validator watching the foregrounded app can conclude the whole LA feature is dead when it isn't; always background the app before judging whether a Live Activity started. *(Observed during the Aug 2026 on-simulator validation sessions, not reproducible from a committed artifact.)*
  - **Two simulators sharing one Metro instance interleave their consoles into one `apps/mobile/logs/dev.log`.** Attribute a log line to a device by cross-referencing the App Group container path that `expo-widgets`' `widgetsDirectory` constant prints — that path names the device UUID. Without this, it's easy to burn time reading one simulator's App Group plist while watching another's logs. *(Observed during the Aug 2026 on-simulator validation sessions, not reproducible from a committed artifact.)*
  - **`com.apple.chrono.WidgetRenderer-Activities` showing up as the client identifier in the accessibility/view hierarchy IS the ActivityKit rendering host, not a stale simulator artifact.** Its presence is positive evidence a real Live Activity is rendering — a validator that reflexively discards it as noise throws away the proof it was looking for. *(Observed during the Aug 2026 on-simulator validation sessions, not reproducible from a committed artifact.)*
- **Where this is recorded:** `docs/screenshots/widgetsandla/INDEX.md` — the "Tooling" section and the `OnTheClock.tsx` header comment are the citable sources for the first four traps; the last three are recorded only here, sourced from the orchestrating session's own agent reports during the Aug 2026 validation work.
- **What not to do:** don't drive a device-specific flow with more than one simulator booted at all — not via the MCP tool, and not via `maestro --udid` either; shut the other one down first. Don't trust a single Maestro screenshot/hierarchy call as ground truth for a specific device — cross-check with `simctl io screenshot` on the exact `udid`. And don't file a regression off a run whose dev.log shows no trace of the action. Don't `simctl terminate` to simulate backgrounding. Don't reach for `ProgressView(timerInterval:)` for anything that must never show seconds — there is no prop combination that suppresses its default label through `@expo/ui`. Don't judge a Live Activity dead from a foregrounded screenshot — background first. Don't read a device's log lines out of a shared `dev.log` without checking which App Group container path they actually belong to. And don't dismiss `com.apple.chrono.WidgetRenderer-Activities` in a view hierarchy dump as leftover noise — it's the thing you're trying to prove exists.

**38. A Live Activity's own body is NOT re-run when iOS redraws it — `expo-widgets` pins `staleDate` to `nil`, so any time-based state change must be poked from the app**
- **Symptom:** the "on the clock" activity's overdue state never appeared. Threshold passed at 10:39:45; at 10:52:14 — 13 minutes later, after several forced redraws — the card was still apricot. Nothing was broken in the comparison, the layout, or the props: the body simply never ran again.
- **Root cause:** the flip is a `Date.now() >= overdueAtIso` comparison inside the `'widget'`-directive body, which only runs when a new ContentState reaches the extension. ActivityKit's mechanism for a scheduled re-render is `staleDate`, and `expo-widgets` hardcodes it to `nil` in all three places it constructs content (`node_modules/expo-widgets/ios/LiveActivity.swift` update + end, `ios/LiveActivityFactory.swift` start) with no prop to override it. So the body re-runs ONLY on an explicit `activity.update()`. Drawing the activity — a lock-screen wake, a long-press, a Dynamic Island expand — does not.
- **Where the fix lives:** `pokeOverdueRedraw()` in `apps/mobile/src/lib/liveActivity.ts` re-pushes the tracked props unchanged, purely to force the re-evaluation; `apps/mobile/src/lib/useLiveActivitySync.ts` arms a `setTimeout` for the instant `resolveOverdueAtMs` gives (the same rule the in-app card and the clock-out reminder flip on) and pokes immediately when the app opens after the threshold has already passed. Running phase only — a receipt has no overdue state to reach. Pinned by `pokeOverdueRedraw` cases in `apps/mobile/src/lib/__tests__/liveActivity.test.ts` and the poke cases in `src/lib/__tests__/useLiveActivitySync.test.ts`.
- **The honest ceiling:** with the app process dead AND never reopened, nothing pokes and the flip waits for the next launch — the clock-out reminder notification is what gets her there. The real fix is a native `staleDate` on the `ActivityContent`, which is a patch to `expo-widgets`, not to this repo.
- **What not to do:** don't assume a time-dependent value inside a Live Activity body updates itself, and don't "verify" it by waking the screen or forcing redraws — those prove nothing about whether the body ran. Anything that must change at a known instant either gets poked from the app or gets a real `staleDate`.

**39. An async "clean up orphans" sweep that ends everything `getInstances()` returns will eventually end the thing the user just started**
- **Symptom:** the Live Activity receipt was missing after clock-out, intermittently — four failures in a row for one validator, a fully-traced success for another, on the same build. Nothing threw, nothing was logged, and the Dynamic Island was simply empty. The receipt was never the broken part: the activity had already been ended seconds after clock-IN, so by clock-out there was nothing left to turn into one.
- **Root cause:** `endIfStillRunning` (`apps/mobile/src/lib/liveActivity.ts`) nulls its tracked handle, then `await`s the lazy `getFactory()` import, then ends every instance `factory.getInstances()` returns. A clock-in landing inside that await starts a new activity that the sweep cannot distinguish from an orphan. Checking `current` after the await is NOT enough — a start that is still awaiting its own factory has not set it yet.
- **Where the fix lives:** a module-level `startGeneration` counter, bumped **synchronously** at the top of `startOnTheClock` before any await; `endIfStillRunning` captures it on entry and bails if `current` is set OR the generation moved. Pinned by "does not sweep away an activity a clock-in started during its own await" in `apps/mobile/src/lib/__tests__/liveActivity.test.ts`, which fails on the unfixed code.
- **Why it looked flaky:** the window is one lazy import wide. A human tapping Clock in seconds after launch never hits it; an automated flow that clocks in immediately after launch hits it repeatedly. "Works when I try it, fails in the harness" is a timing signature, not a harness artifact — reproduce it as a deterministic interleaving in a test rather than by re-running the device.
- **What not to do:** don't write a cleanup sweep whose selector is "everything the platform currently holds" without a happens-after guard, and don't rely on nulling shared state before an await as that guard — the state is back before you look at it.

**40. A toast is invisible over an open `BottomSheetBase` — a refused write inside a sheet must render inline**
- **Symptom:** a nanny fixes a wrong time on Hours, taps Save, the spinner stops, the sheet stays open — and nothing else happens. Same for "Add missed hours". The API log showed the request being refused every time (`400 VALIDATION_ERROR reason=CLOCK_SPAN_TOO_LONG`); the app was calling `showErrorToast` on every one of them.
- **Root cause:** `toastify-react-native`'s `ToastManager` renders inside its own React Native `<Modal>` (`useModal` defaults to `true`, and `apps/mobile/src/app/_layout.tsx` doesn't override it). `BottomSheetBase` is *also* an RN `<Modal>`. Presenting a second modal window over an already-presented one is not reliable on iOS — same family as #1. So every mutation refusal raised while a sheet was open was reported to a surface the user could not see.
- **Not fixable by `useModal={false}`:** that renders the toast in the JS tree instead, which puts it *behind* the presented modal rather than in a competing window. Either way the sheet wins. The toast is only reliable for callers with no sheet open.
- **Where the fix lives:** `apps/mobile/src/domains/timesheet/utils/timeEntryWriteError.ts` (`describeTimeEntryWriteError`) turns a refusal into one localized message plus the conflicting entry's id; the three writing sheets render it themselves — `ClockOutSheet`'s `submitError`/`submitErrorAction` props, and `AddMissedHoursCard`'s `today-missed-hours-error`. The mutation hooks keep their toast for non-sheet callers.
- **What not to do:** don't report a failure with a toast from inside a `BottomSheetBase`, and don't take "the hook already toasts it" as evidence the user saw anything. If a sheet can be open when the error lands, the sheet has to show it. Prefer blocking the submit client-side where the server's rule is knowable — `ClockOutSheet` now checks the shared `MAX_SESSION_SPAN_MS` before the request rather than after.

**41. `shiftInstantsFromWallClock`'s next-day roll needs a ceiling in any caller that has one**
- **Symptom:** editing a time entry to a finish earlier in the day than the start produced a ~22.5h shift and a `CLOCK_SPAN_TOO_LONG` 400 — a start of `06:53` with a finish typed `05:27` became `2026-08-04T06:53Z → 2026-08-05T05:27Z`.
- **Root cause:** `apps/mobile/src/lib/wallClock.ts`'s `shiftInstantsFromWallClock` rolls `endTime <= startTime` onto the next calendar day. That is correct for shift editing (a 19:00–00:30 shift really does end tomorrow) and it is what makes an overnight correction possible at all. But the rolled span is `24h − (start − finish)`, so it clears the server's 16h `MAX_SESSION_SPAN_MS` only when the finish is at least 8 hours earlier than the start. Every value inside that 8-hour window was a guaranteed 400 — and the roll was invisible, so a carer who typed `527` meaning 5:27 pm had no way to see what the app had decided.
- **Where the fix lives:** `MAX_SESSION_SPAN_MS` moved to `packages/shared-types/src/schemas/timesheet.schema.ts` so client and server share one number; `ClockOutSheet` blocks the submit with `clockout-too-long-error` and labels a legitimate roll with `clockout-overnight-hint` ("Finishes 5 Aug"), so the day it lands on is never implicit.
- **What not to do:** don't reuse the roll in a surface with a span limit without checking the limit, and don't leave a roll unlabelled — an overnight entry and a mistyped one look identical in two HH:MM fields. Don't fix it by removing the roll: `ShiftDetailScreen` and the nanny counter-offer depend on it.

**42. `@rn-primitives/*` (Collapsible, Accordion, and siblings) fails to parse under `bun:test` — its RN entry point ships JSX-preserved `.mjs`/`.js`, and Bun picks the JSX transform from the file extension, not the content**
- **Symptom:** `error: Unexpected <` at `node_modules/@rn-primitives/accordion/dist/accordion.mjs:26:10` (or the equivalent path for `collapsible`, `select`, `dropdown-menu`, or any other `@rn-primitives/*` package) the moment a test file's module graph reaches a component built on one — even a component that renders successfully in the real Metro-bundled app.
- **Root cause:** these packages' `package.json` `exports` map both the `import` (`dist/*.mjs`) and `require` (`dist/*.js`) conditions to tsup output built with `jsx: "preserve"` — raw JSX left untransformed, meant for Metro's own Babel pass at bundle time. Bun's test loader infers its JSX transform from the file EXTENSION (`.tsx`/`.jsx` get it, `.mjs`/`.js` do not), never from the file's actual contents, so it hands the raw JSX straight to its non-JSX parser and dies on the first `<`. This is a gap between Bun's loader and this dependency family's distribution shape — not a defect in whatever component imports it, and it reproduces for ANY `@rn-primitives/*` package, confirmed for both `collapsible` and `accordion` while building 3-U1's `TermGroup`.
- **Where the fix lives:** nowhere yet — no existing component in this repo (`apps/mobile/src/components/ui/accordion.tsx`, `collapsible.tsx`, `select.tsx`, `dropdown-menu.tsx`, …) has a test that renders it, so nothing had hit this before. `TermGroup.tsx` (`apps/mobile/src/domains/pay/components/`) works around it by using plain `useState` + `Pressable` instead of either primitive — see that file's module doc for the full reasoning and what was given up (the chevron's 180ms rotation animation; it still flips, just instantly).
- **What not to do:** don't assume a `@rn-primitives/*`-based component is untestable and skip its test — the workaround (rebuild the one piece you need on plain React state/RN primitives) is usually small. Don't "fix" this by mocking the whole `@rn-primitives/*` module in every test file that touches one of these UI components either — that stops testing the component's actual structure. A real fix (a Bun loader override, or asking upstream for a transformed dist target) would remove the need for the workaround; nobody has built one yet.

### API / LLM

**9. LLM prompts can leak PII into logs, third-party providers, or Sentry**
- **Symptom:** a user's name (or other PII passed into a prompt) shows up in a stored LLM response, a log line, or an error report.
- **Root cause:** without deliberate masking, whatever you interpolate into a prompt can come back verbatim in the model's output or in error context.
- **Where the fix lives:** `apps/api/src/domains/llm/services/llmGenerate.ts`'s `generateLlmObject<T>` takes a `pii` option (`'none' | 'maskOnly' | 'maskAndUnmask'`); the masking itself is `maskPII` in `apps/api/src/utils/piiMasking.ts`, which replaces the given name with a generic `[NAME]` placeholder (`DEFAULT_PLACEHOLDER`) before the prompt goes out, and can unmask it back into the response afterward for `maskAndUnmask` callers.
- **What not to do:** don't interpolate a raw name/PII value directly into a prompt string — always pass through `generateLlmObject`'s `pii` option (or call `maskPII` yourself if you're not using that helper) so masking happens before the request leaves the process.

**10. Gemini's "thinking" mode silently adds seconds of latency to structured-output calls**
- **Symptom:** a "fast" LLM call takes 3–6+ seconds longer than expected with no visible error.
- **Root cause:** Gemini 2.5 models default to an internal "thinking" pass even for simple structured-output requests, which is wasted latency on latency-sensitive paths.
- **Where the fix lives:** `apps/api/src/config/llmProvider.ts`'s `LlmCallConfig` interface exposes `disableThinking`; `app.llmConfigs.ts`'s example bundles (`widgetDescriptionConfig`, `widgetSummaryConfig`) both set `disableThinking: true`. The same config also bounds `timeoutMs` (enforced via `AbortController` in `generateLlmObject`) and `maxRetries`, so a slow call can't silently blow through your timeout budget via the SDK's own retry back-off.
- **What not to do:** don't add a new `LlmCallConfig` bundle without deciding `disableThinking` and `timeoutMs`/`maxRetries` deliberately — the defaults matter for cost and latency, not just correctness.

**11. Atomic quota / usage-counter races**
- **Symptom:** two concurrent requests both pass a usage-limit check and both proceed, silently exceeding the intended cap (check-then-increment race).
- **Root cause:** checking a counter and incrementing it in two separate steps is a classic TOCTOU (time-of-check-to-time-of-use) bug under concurrency.
- **Where the fix lives:** `supabase/migrations/006_subscriptions_usage_email.sql`'s `check_and_increment_usage` RPC does the check-and-increment atomically inside one SQL function (`SECURITY INVOKER`, locked to `service_role` only); `increment_usage_counter` is the plain atomic-increment counterpart.
- **What not to do:** don't reintroduce a "read the counter in app code, then write it back" pattern for anything gating a quota — always go through the atomic RPC.

**12. Push notifications silently drop provisional-permission devices**
- **Symptom:** a real, working device token exists for a user, but they never receive a push — no error anywhere.
- **Root cause:** iOS's "provisional" notification authorization (quiet, no-prompt delivery) is a legitimate, deliverable permission state, but a naive delivery query that only checks for `'granted'` silently excludes every provisional device.
- **Where the fix lives:** `apps/api/src/domains/notification/constants.ts`'s `DELIVERABLE_NOTIFICATION_PERMISSIONS = ['granted', 'provisional']`, imported wherever a delivery query filters by permission (currently `notification/types/index.ts` and `notification/repositories/deviceRepository.ts`). The constant's own doc comment warns this set is push-specific — don't reuse it to gate email deliverability, which has separate rules.
- **What not to do:** don't hand-write `.eq('notification_permission', 'granted')` in a new delivery query — import and use the shared constant so a future permission-state addition only needs one edit.

**13. RevenueCat webhook 500s with "permission denied for table users"**
- **Symptom:** the RevenueCat webhook endpoint intermittently (or always) 500s, and the API logs show a Postgres permission-denied error on `auth.users`.
- **Root cause:** a `SECURITY INVOKER` SQL function that probes `auth.users` (e.g. to check a user exists) runs as whatever role invoked it — here, `service_role` — which doesn't have `SELECT` on `auth.users` by default.
- **Where the fix lives:** `supabase/migrations/006_subscriptions_usage_email.sql`'s `process_subscription_event` — replaces the `auth.users` existence probe with a NULL-guard plus an exception handler that catches a `foreign_key_violation` (an unknown user) and treats it as a benign skip instead of a hard failure; the function itself is idempotent (`ON CONFLICT (event_id) DO NOTHING`) and is revoked from `public`/`anon`/`authenticated`, granted only to `service_role`.
- **What not to do:** don't add a direct `auth.users` lookup inside a webhook-handling SQL function — treat foreign-key failures against user-scoped tables as the "user doesn't exist" signal instead.

**24. A one-phase "claim" ledger turns a process death into a permanently swallowed notification**
- **Symptom:** a carer never gets a shift reminder, forever. No error, no retry, nothing in the logs — the job runs green every night and simply skips her.
- **Root cause:** the dedupe ledger was a single row written *before* the send (`INSERT (user_id, reminder_key)` wins the claim, a duplicate insert loses it). That makes the claim and the delivery one phase: if the process dies between winning the claim and the push actually going out, the row survives, and every future run reads it as "already sent". A `catch`-based release cannot help — `kill -9`, OOM and host loss skip `catch` blocks. The bug this shape was introduced to fix (writing the log row before checking quiet hours / opt-out / device tokens) is the same failure by a different door.
- **Where the fix lives:** a two-phase ledger — **claim → send → confirm**. `supabase/migrations/060_reminder_confirmed_at.sql` adds a nullable `confirmed_at` to `push_reminder_log`; `reminderJob.ts`'s `claimAndSend` (`:405`) claims, sends, then calls `log.confirm(...)` (`:440`) in its own isolated `try/catch` so a failed confirm can never re-enter the release path; `reminderLogRepository.ts` holds `confirm()` (`:106`) and `sweepStaleClaims()` (`:133`), which deletes unconfirmed claims older than `STALE_CLAIM_HOURS = 2` (`:34`). The sweep runs **once at job start, before anything is claimed** (`reminderJob.ts:699`). Pinned by `it('sweeps stale claims once, before anything is claimed')` and `it('does not send a delivered reminder into the release path when confirm fails')`.
- **The backfill-or-nuke trap:** the migration ends with `update public.push_reminder_log set confirmed_at = sent_at where confirmed_at is null;` (`060:44-47`), and that line is load-bearing. Every pre-existing row is legitimately delivered but unconfirmed, so without the backfill the *first* sweep after deploy deletes the entire historical ledger and every reminder in it re-fires. Equally, do not give the column a `now()` default — then nothing is ever sweepable and the two phases collapse back into one.
- **What not to do:** don't treat "the row exists" as "the work happened" for anything whose absence is silent. When you add a phase-two column to a dedupe table, decide the fate of existing rows in the *same* migration — backfill them as done, or accept that the first sweep nukes them. And don't add a `default now()` to a column whose whole job is to be null for a while.

**25. PostgREST returns `+00:00`, JS writes `.000Z` — a string compare of two identical instants is wrong**
- **Symptom:** a guard that compares two timestamps lets through (or wrongly rejects) a case it was written to catch, and only for rows that made a round trip through the database. Locally, with freshly constructed dates, it passes.
- **Root cause:** the same instant has two legal ISO-8601 serialisations. Postgres/PostgREST hand back `timestamptz` as `2026-08-03T08:00:00+00:00`; anything built in JS via `toISOString()` is `2026-08-03T08:00:00.000Z`. They are the same moment and are **not** the same string — `'2026-08-03T08:00:00+00:00' === '2026-08-03T08:00:00.000Z'` is `false`, and `<` / `>` between them are lexicographic nonsense. The failure is invisible in any test whose fixtures were all written in one style.
- **Where the fix lives:** compare instants, never strings — `new Date(a).getTime()` on both sides. Two occurrences so far, both found the hard way: `shiftCommandService.ts`'s effective-range check (pinned by `it('compares the effective range chronologically, not as strings', ...)`, `apps/api/tests/unit/domains/shift/services/shiftCommandService.test.ts:178`), and — the second occurrence, and the more expensive one — the C6 crash-safe adoption path, `findAbandonedFragment` (`timesheetCommandService.ts:795`), which matches an orphaned week-split fragment on `new Date(row.clock_in_at).getTime() === boundaryMs`. Written as a string compare it matched nothing, so the adoption path was **dead code**: every retried clock-out re-split the session instead of adopting the fragment already on disk, and the carer stayed locked out. Pinned by `it('adopts an orphan written with our own .000Z formatting too', ...)` — which exists precisely because the first version of that test only used PostgREST-shaped fixtures and passed against the broken code.
- **What not to do:** never `===`, `<` or `>` two timestamp strings, even when both "look like ISO". Don't use `.toISOString()` output as a lookup key against a column PostgREST serialises. And when you write the test, use **both** serialisations in the fixtures — one style proves nothing.

**26. `bun` and Metro both fall back to the PRODUCTION `.env` unless every var is explicitly exported**
- **Symptom:** a test suite, script, or simulator you believe is pointed at the local stack is reading and writing **production**. Nothing warns you. It works perfectly, which is the problem.
- **Root cause:** `bun` auto-loads `apps/api/.env`, and Expo/Metro falls back to `apps/mobile/.env`, whenever the corresponding variable is not already set in the environment. Set *some* of the vars and you get a silent mix — local URL, production key, or the reverse. A **long-lived dev server is the dangerous case**: nothing re-reads its environment, so a Metro started days ago keeps serving whatever it resolved at boot, and neither the simulator nor the app shows which backend is behind it.
- **Where the fix lives:** a hard guard at the point of use, not a convention. `apps/api/tests/integration/rls.integration.test.ts:59` refuses to run unless the host is `127.0.0.1`, `localhost` or `::1` — the test aborts rather than trusting its environment. Copy that shape into anything that writes.
- **Bitten three times in one session:** an RLS run that created and deleted real users in production (cleaned up, verified); the same mechanism caught before it acted; and a stale Metro found serving production Supabase to a simulator during mobile validation.
- **What not to do:** don't assume a local `SUPABASE_URL` in your shell covers you — check the *key* too, since they load independently. Don't reuse a dev server across sessions when the backend may have changed; kill and restart it. And never rely on "I exported the right vars" for anything destructive — put the assertion in the code, where it runs every time.
- **Update (audit closeout, 2026-08-06) — the root cause above is incomplete, and suppressing `bun`'s auto-load does NOT protect you.** This app loads `.env` a **second time, explicitly**, and no `bun` flag can suppress that: `apps/api/src/config/env.ts:28` and `apps/api/src/instrument.ts:19` both call bare `dotenv.config()`. Three properties of those two calls decide the outcome. Neither passes a `path`, so dotenv resolves `<process.cwd()>/.env` — the production file, whenever the process is started from `apps/api`. Neither passes `override: true`, so dotenv's default `override: false` applies: an **exported** var wins, an **unexported** one silently takes the production value. And `instrument.ts` is `--preload`ed, so it fires *first*, before any application code can assert anything. That is exactly the "silent mix" described above, arriving through a door the root-cause note never named — so "I disabled the runtime's env auto-loading" is not a defence, and reaching for a flag instead of exporting the variables is how this becomes bite five. **What actually protects a run is both halves together: launch from a directory with no `.env` beside it, AND export every variable the process reads.** The hard guard at the point of use (above) remains the only thing that protects you when you get both wrong.

- **Update (2026-08-07) — the mirror image also breaks the app, and it presents as a LOGIN bug.** The reverse mix (API on the **local** stack, mobile on **production**) does not corrupt data — it locks you out. Sign-in *succeeds*: Supabase returns a valid ES256 JWT. Then `validateSupabaseToken` asks the **local** Supabase to verify a **production**-signed token, which can never work, so every authenticated call 401s and the client's retry-then-`onUnauthorized` path logs `[API] 401 after retry - signing out` and bounces the user back to the welcome wall. It reads exactly like "login is broken". Cost: a dev server that had held stale exported `SUPABASE_URL`/`ANON`/`SERVICE`/`DB_URL` for 17 hours while `apps/api/.env` on disk said production the whole time — `ps eww -p <pid>` is what settles it, because the on-disk `.env` will look correct. The startup banner in `apps/api/src/config/supabase.ts` cannot catch this: it only fires on dev-pointed-at-remote and has no idea which project the *client* uses. **The guard now lives in `apps/api/src/middlewares/auth.ts`** (`mismatchedIssuerHost`): on a failed `getUser`, it decodes the JWT's `iss` claim and, when the issuer host disagrees with `env.SUPABASE_URL`, logs `SUPABASE PROJECT MISMATCH` naming *both* hosts instead of the generic `Invalid or expired token`. The 401 sent to the client is byte-identical either way, so nothing leaks. Tests: `apps/api/tests/unit/middlewares/authIssuerMismatch.test.ts`.
- **Update (2026-08-12, Phase 6) — "`ps eww -p <pid>` is what settles it" is WRONG when more than one server is alive, and that sentence above cost two sessions an hour each.** `ps eww` proves a process's environment; it says **nothing** about whether that process owns the port. Found during Phase 6: **five** `bun --watch` API processes alive simultaneously, **four with no explicit `SUPABASE_URL`** (so all four fell through to `apps/api/.env` = production), and the one process that *was* correctly exported for the local stack **was not the listener**. `:8080` was held by an orphaned Aug-10 process (`PPID 1`, its parent shell long gone) that had bound the port days earlier. Whoever binds first keeps it; later servers stay alive having silently failed to bind, and `--watch` will rebind an old process into the gap when the correct one is restarted — so the wrong server can *become* the listener hours after you thought you fixed things.
  - **The log actively misleads you**, because every one of those servers `tee`s into the same `apps/api/logs/dev.log`. A healthy `Server running on port 8080` line can come from a different process than the one serving, and a real `DEV SERVER POINTED AT A REMOTE DATABASE` banner can be waved away as historical. **Truncate `logs/dev.log` before restarting**, or nothing in it is evidence.
  - **Presentation:** `mismatchedIssuerHost` fires (`SUPABASE PROJECT MISMATCH`), every authenticated request 401s, and the app concludes the session is dead and drops to the welcome screen. In an E2E suite that reads as an app defect or a flaky flow — a Maestro flow died on `assertVisible: pay-setup-screen` with the app sitting on `welcome-screen`, and the real cause was three directories away.
  - **The check that actually holds — port first, pid second:**
    ```
    lsof -nP -iTCP:8080 -sTCP:LISTEN                      # the pid that ACTUALLY serves
    ps eww <that pid> | tr ' ' '\n' | grep '^SUPABASE_URL='
    ```
    Then prove it **functionally** rather than by inspection: mint a token from the local stack (`POST /auth/v1/token?grant_type=password`) and `curl` an authenticated endpoint — `200` is proof, `401` means you are talking to production. To clean up, `kill -9` every stale API pid **including the `bash -c` wrapper** (or `--watch` respawns it), confirm `:8080` is empty, then start exactly one. Same procedure for Metro on `:8081`.

**27. Accepting a new "usual week" must SUPERSEDE the old one, or every accepted pattern keeps generating shifts forever**
- **Symptom:** the same shift shows up two or three times on the parent's Today/Schedule tabs — byte-identical date and time — and the week's totals could eventually pay twice for one worked window.
- **Root cause:** two halves. (1) `schedulePatternCommandService.respond`'s accept branch flipped a pattern to `accepted` without ending the previously accepted pattern for the same (household, carer) — migration 014 always *defined* `ended` as "superseded or past its `until` date", but only the `until` half was ever implemented, so a household silently accumulated live patterns (three at once, in practice). (2) Materialisation dedupes per `source_pattern_id` (`findByPatternAndDate`), so each live pattern materialised its own identical `shifts` row, invisible to the others. A third leak compounded it: nothing withdrew an `ended` pattern's already-materialised future shifts, so even ended patterns left confirmed shifts stranded months out.
- **Where the fix lives:** `schedulePatternCommandService.ts` — `supersedePriorAccepted` (called from the accept branch *before* materialising) and the single `endPattern` helper every end-path routes through, which also cancels the pattern's future `system_generated` shifts via `scheduleMaterialisationService.cancelFutureShiftsForEndedPattern` (past, completed, and clocked-into shifts are never touched). DB backstop: migration `062_recurring_shift_dedupe.sql` — a partial unique index `shifts_recurring_window_unique` on `(household_id, carer_id, starts_at, ends_at) nulls not distinct where kind='recurring' and status <> 'cancelled'`, mirroring 059's extra-shift index, after a one-time cleanup that ended stale accepted patterns and cancelled 33 duplicate rows. On 23505 the materialiser ADOPTS the existing row (re-points `source_pattern_id`; never re-keys `ical_uid` — that's the device-calendar marker, #16) instead of failing the run.
- **What not to do:** don't "fix" duplicates by deduping in the query layer or the UI — the rows are real and payroll-adjacent, so they must not exist. Don't extend this into an overlap/exclusion constraint: overlapping shifts are deliberately legal (015's "NO OVERLAP CONSTRAINT, DELIBERATELY"; clashes warn, never block) — only the *identical* window is refused. And if a state machine's comment says a status means "superseded or X", grep for the code that writes it for *each* meaning before trusting it.

**28. A remote database charges per ROUND TRIP, not per row — a per-day loop made accepting a usual week take 26 seconds**
- **Symptom:** `POST /api/v1/schedule-patterns/:id/respond` returned 200 with perfectly correct data (supersede fired, shifts adopted, zero duplicates) after **26,051 ms**. Nothing was slow locally, no query was slow, and no log line pointed anywhere: the time was spread evenly over ~130 individually-fast statements.
- **Root cause:** `scheduleMaterialisationService.materialise` asked the DB a question *per occurrence* — `findByPatternAndDate`, `hasTimeEntries`, `hasChangeRequests`, `create`, then two more for `replaceChildren` — and `cancelFutureShiftsForEndedPattern` asked two per prior shift. Over the 84-day `MATERIALISATION_HORIZON_DAYS` a 2-day/week pattern is 24 occurrences, so accepting one cost 73 round trips to materialise plus 49 to supersede. Hosted Supabase is ~150-200ms away; 122 × ~200ms *is* 26 seconds. Measured, not guessed: `73 → 5` and `49 → 3` after the fix, and the arithmetic reproduces the observed wall clock to within 3%.
- **Where the fix lives:** `scheduleMaterialisationService.ts` is now partition-then-batch — one `findActiveByPattern` read indexed by `local_date` in memory (it was already being read for reconciliation, so the per-occurrence lookup was pure waste), one `shiftIdsWithTimeEntries` + one `shiftIdsWithChangeRequests` probe for the whole run, `createMany`/`replaceChildrenMany` for new rows, `deleteMany`/`updateMany` for orphans (their cancel patch is identical by construction). The only per-shift statement left is the times-moved `update`, whose patch genuinely differs, at `UPDATE_CONCURRENCY` 8. A multi-row insert is one statement, so a 23505 aborts the lot without saying which row lost: `createMany` therefore returns `null` (never throws) and the service retries row by row, where the collision is attributable and #27's adopt path still works. `respond`/`amend` also stopped calling `getWithDays` (re-reading a pattern they hold and re-checking membership they already checked) in favour of `getDaysForPattern`. Pinned by `tests/unit/domains/schedule/services/scheduleMaterialisationBatching.test.ts`, which asserts the repository-call count is IDENTICAL for a 1-week and a 52-week horizon.
- **While in there, #25 bit again:** the times-moved check was `existing.starts_at !== occ.startsAt` — PostgREST `+00:00` against a JS-built `.000Z`, so every unchanged shift looked moved and every horizon run silently reverted the carer's accepted week to `pending`. Fixed to compare `getTime()`; the regression test uses a `+00:00` fixture deliberately.
- **What not to do:** don't reach for a background job or a "return early and finish later" trick before counting round trips — the UI refetches shifts immediately after this call, so the near-term rows must be committed before the response. Don't measure with locally-constructed fixtures: every statement here is <5ms against a local DB and the bug is invisible. And when you add a branch to this service, add it to a partition plus a batch call — never an `await` inside a loop over occurrences.

**29. A shift's UTC instant is derived from `schedule_patterns.timezone`, NOT `households.timezone` — and the two legitimately disagree**
- **Symptom (the false alarm):** a freshly materialised Monday 09:00–17:00 pattern was stored `starts_at 2026-08-10 16:00+00, ends_at 2026-08-11 00:00+00`. 16:00Z–00:00Z is 09:00–17:00 in `America/Los_Angeles` — *the zone of the machine the dev server runs on* — while every shift the same household had from earlier in the week was stored `08:00Z–16:00Z`, i.e. 09:00–17:00 `Europe/London`. It reads exactly like #28's batching rewrite silently switched the wall-clock→UTC conversion to server-local, mid-flight, on money-bearing rows. It did not. **Both sets of rows were correct.**
- **Root cause of the misreading:** `schedule_patterns.timezone` is a **snapshot** of `households.timezone` taken once, when the draft is created (`schedulePatternCommandService.createDraft`, `const timezone = household?.timezone ?? 'UTC'`), and it is never re-synced afterwards. This household's zone was changed `Europe/London → America/Los_Angeles` partway through the week, so patterns drafted before the change still carry London and patterns drafted after carry Los Angeles — and each one's shifts are right *for its own pattern*. Checking a shift against the household's **current** zone therefore flags every pre-change row as corrupt. On the hosted DB that was 58 of 94 live recurring shifts.
- **The integrity check that is actually true** — join the pattern, not the household, and let Postgres do the DST math:
  ```sql
  -- A weekday may carry MORE THAN ONE block since 101, so this must ask
  -- "does SOME block on this weekday explain this shift's instant?" — a plain
  -- join fans out to one row per block and the `<>` filter then matches the
  -- OTHER block, reporting every split day as corrupt. That false positive is
  -- exactly the kind of misreading this entry exists to prevent.
  select s.id, s.starts_at, p.timezone
  from shifts s
  join schedule_patterns p on p.id = s.source_pattern_id
  where s.kind = 'recurring' and s.status <> 'cancelled'
    and not exists (
      select 1
      from schedule_pattern_days pd
      where pd.pattern_id = p.id
        and pd.weekday = extract(dow from s.local_date)
        and s.starts_at = ((s.local_date::text||' '||pd.start_time::text)::timestamp
                             at time zone p.timezone)
    );
  ```
  It returns **zero rows**, and did so all through the alarm. Run it before believing any "materialisation wrote the wrong instant" report.
- **Where the conversion actually lives (and why batching couldn't have moved it):** `recurrenceExpander.zonedWallTimeToUtcMillis` — the only wall-clock→UTC conversion in the domain, parameterised on `pattern.timezone`, offset re-derived per date via `Intl` (#21). `expandRecurrence` returns absolute UTC instants; `scheduleMaterialisationService`'s batched `createBatch`/`newShiftRow` only *copies* `occ.startsAt`, and `shifts.local_date` is derived by 015's `sync_shift_local_date` trigger from the row's own `timezone` column. There is structurally no zone-free wall-clock arithmetic in `materialise`, `cancelFutureShiftsForEndedPattern` or the adopt path — every comparison there is `new Date(...).getTime()` on two absolute instants.
- **The near-miss worth remembering:** the proposed remedy was a repair migration that recomputed `starts_at`/`ends_at` with `at time zone households.timezone`. Applied, it would have shifted **58 correct, payroll-bearing shifts by 8 hours** — the "fix" was the only data corruption on the table. Verify the premise against the DB *before* writing the repair, not after.
- **Test gap this did expose (now closed):** every fixture in `scheduleMaterialisationBatching.test.ts` and `scheduleMaterialisationService.test.ts` handed `materialise` hand-written occurrence literals (`${localDate}T07:00:00.000Z`), so 18+8 tests would have passed byte-for-byte against a genuinely server-local conversion. The last block of `scheduleMaterialisationBatching.test.ts` now drives the **real** `expandRecurrence` through the **real** batch with `process.env.TZ` pinned away from the pattern's zone, asserting 09:00 London → `08:00Z` in August and `09:00Z` in January. Verified by mutation: hardcoding the process zone into the expander turns those two red (reproducing the exact `16:00Z` from the report) while all eight pre-existing batching tests stay green. The expander's own test file does catch it — the hole was only at the service layer.
- **~~Open product question~~ — DECIDED (D-10, verified in 3-T3).** Because the snapshot never re-syncs, a family that moves timezones keeps getting their old zone's instants from an already-accepted pattern until it is re-drafted. **That is the answer: silent status quo, no prompt, no repair, no re-sync.** A pattern's wall-clock times were agreed in a specific zone, and the "obvious" repair is the one that would have shifted 58 correct payroll-bearing shifts by 8 hours. Verified in the tree as of 3-T3: the only timezone dialog anywhere is `ManageHouseholdScreen`'s confirm-before-save on the household's own field, and its copy already states the status quo rather than offering to fix anything — *"This only affects new schedules and how 'this week' is calculated going forward. Shifts and hours you've already recorded keep the time zone they were created in and will not change."* (`household.json` `householdSettings.timezoneConfirmBody`). Nothing prompts to re-sync a pattern; nothing should. If you are here because you want to add "sync pattern zone to household" logic, D-10 says no — reopen it with the owner first, not in a refactor.
- **What not to do:** don't diagnose a timezone bug from the shape of the numbers alone — "16:00Z is 09:00 on my laptop" is a coincidence a US-Pacific dev machine will hand you constantly, and both zones being plausible is not evidence. Don't repair timestamps against a mutable parent column when the child row (or its pattern) carries its own zone. And don't trust a passing suite as proof a conversion is zone-correct until one fixture crosses a zone.

**31. PostgREST `ignoreDuplicates` cannot cover an EXPRESSION index — the "idempotent" bulk insert 23505s and loses every row, including the new ones**
- **Symptom:** a batch insert written to be safely re-runnable throws `23505` instead of skipping the duplicates, and the entire batch is lost — not just the colliding row. Because the caller treated the insert as idempotent, the *new* rows in that batch are dropped silently along with the duplicate, and whatever the batch fed (a push, a count, a downstream write) sees nothing.
- **Root cause:** `.upsert(rows, { ignoreDuplicates: true })` compiles to `ON CONFLICT DO NOTHING`, and Postgres only applies that to the **conflict target** PostgREST names. PostgREST's `onConflict` option accepts a **column-name list only** — it has no syntax for an expression. So a unique index over an expression (here `shift_events_keyed_unique_idx`, `supabase/migrations/025_shift_events_keyed_unique.sql:21-23`, which is both partial and keyed on `(payload->>'key')`) can never be named as the conflict target, `ignoreDuplicates` does not apply to it, and a concurrent duplicate makes the **whole statement** raise instead of being skipped. A multi-row insert is one statement, so one loser takes the batch with it. This was verified against local PostgREST 14.15 — and worth knowing: the previous version of the comment on this very function claimed the opposite, from an unreproducible manual check, which is how the finding stayed closed while the bug stayed live.
- **Where the fix lives:** catch the 23505 and retry row by row, where the collision is attributable. `apps/api/src/domains/shift/repositories/shiftEventRepository.ts:177-213` — batch attempt, bail out to the row loop only on `UNIQUE_VIOLATION`, then per row `continue` on `isKeyedDuplicate(rowError)` (`:49-58`) and throw on anything else. Note the asymmetry, and keep it: the **batch** check is on the bare error code (it only decides whether retrying is worth trying), while the **per-row** skip additionally requires the message to name `shift_events_keyed_unique_idx`, so a 23505 from any other index still surfaces instead of being swallowed as "already there". The method returns only rows it genuinely created, which is what lets `uncoveredCareService.ts` push for newly-raised uncovered care only. Same family as #28's `ScheduleShiftRepository.createMany` (`scheduleShiftRepository.ts:205`) but the opposite division of labour: `createMany` returns `null` and the **service** retries; `insertMany` retries **internally**.
- **What not to do:** don't treat `ignoreDuplicates: true` as "this insert is now idempotent" without checking what index it would actually conflict on — if that index is partial-on-an-expression or otherwise unnameable as a column list, the flag buys you nothing. Don't skip a 23505 on the bare error code in a row-by-row retry; name the index, or an unrelated constraint violation becomes a silently dropped row. And don't fire a notification off the rows you *asked* to insert — fire it off the rows the insert says it created.

**32. An ownership cache keyed on `(user, resource)` with no lookup identity lets a permitted READ poison the entry a WRITE check would use**
- **Symptom:** a caller who may only read a resource performs an action on it that they must not be allowed to perform — and only after they have read it once. Cold, the action is correctly refused. The escalation is invisible in any test that exercises one route at a time, because it needs two routes and an ordering.
- **Root cause:** `makeOwnershipValidator` (`apps/api/src/middlewares/validateResourceOwnership.ts`) caches the result of its `lookup` under `getRelationshipKey(userId, resourceId)` (`:85` → `apps/api/src/utils/cache.ts:45-49`), and **the lookup function's identity is not in the key**. Two validators over the same URL param therefore share one entry, first writer wins: mount a *wide* lookup (may this user see it?) on `GET /:id` and a *narrow* one (may this user change it?) on the actions, and one permitted GET writes a positive entry that every subsequent action reads and short-circuits on (`:88-104`), skipping its own stricter check entirely. It is not a per-request cache — `cache.ts:10-14` is a module-level process-wide `NodeCache` and the positive TTL is **one hour** (`:22`, `RELATIONSHIP: 3600`), so the poisoned entry outlives the request, the session, and the membership. Reproduced against the router during this work: a **removed** parent, one permitted `GET /timesheets/:id`, then `approve` on the same id — 200, and a week approved by someone with no active membership. One id, two different permissions, one cache key.
- **Where the fix lives:** for now, by **not using the middleware** where the two permissions diverge. `apps/api/src/domains/timesheet/routes/timesheetRoutes.ts:42-53` registers `GET /:id` with **no** ownership middleware and a comment stating why; the read does its own gating inside the service (`timesheetQueryService.ts:174-179`), so nothing ever writes the entry the actions would reuse. Pinned by `it('a permitted GET followed by approve on the SAME id still 404s')` (`tests/unit/domains/timesheet/routes/timesheetRoutes.test.ts:199`). The real fix — fold the lookup's identity into the cache key — is one line in `getRelationshipKey` plus a discriminator argument at every `makeOwnershipValidator` call site, and it is what should happen the moment a second route pair needs it.
- **What not to do:** don't wire a wide read lookup into `makeOwnershipValidator` on a resource whose actions use a narrower one — that is the exact shape, and it silently *removes* a guard rather than duplicating it. More generally: never key an authorization cache on the subject and the object alone. The cached answer is to a **question**, and two different questions about the same pair have different answers, so the question belongs in the key. And don't reason about it as a request-scoped memo — check the TTL before you assume the blast radius is one request.

**33. A full button class string handed to a label `<Text>` steals the touch responder — the button underneath goes inert**
- **Symptom:** a confirm button does nothing on device. The dialog stays open, no handler runs, no error anywhere. Its sibling buttons on the same screen work, and every unit test passes.
- **Root cause:** `AlertDialogAction` passed the caller's `className` into `buttonTextVariants({ className })` — i.e. it fed a **button** class string into the **label text's** class context. The two call sites that hit it passed `buttonVariants({ variant: 'destructive' })`, so the inner `<Text>` received `bg-destructive active:opacity-90 h-10 px-4 …`. The `active:` is the killer, and the mechanism is a two-library handshake: `react-native-css-interop` compiles `active:`/`hover:`/`focus:` into ruleset flags and at runtime attaches `onPressIn`/`onPressOut` **plus a deliberate `onPress` shim** (its own source says "Some React Native components (e.g Text) will not apply state event handlers if `onPress` is not defined"). It does NOT set `onStartShouldSetResponder` — **React Native's `Text` does that itself**: `isPressable = onPress != null` wires up Pressability, whose `onStartShouldSetResponder` returns true. Responder negotiation runs deepest-first, so the label wins the touch over its ancestor `Pressable`. The shim then forwards to `originalProps.onPress`, which the Text does not have, so the tap is swallowed entirely — inert, not mis-targeted. Buttons whose label classes only carry `group-active:` are unaffected: those resolve off the parent and attach nothing to the Text.
- **Where the fix lives:** `apps/mobile/src/components/ui/alert-dialog.tsx` — `AlertDialogAction` and `AlertDialogCancel` no longer forward `className` into `buttonTextVariants()`. The button still receives it via `cn(buttonVariants(), className)`. Pinned by `apps/mobile/src/components/ui/__tests__/alert-dialog.action.test.tsx` (`keeps a caller button className off the label text`).
- **Why no test caught it, which is the more useful half:** `bun.setup.ts` stubs `buttonVariants`/`buttonTextVariants` to `mock(() => '')`, so **every button class string in every mobile test is empty** — no test in this repo can observe a leaked class. It also stubs the whole css-interop runtime, so handler injection never happens; and RTL's `fireEvent.press` calls `onPress` directly instead of doing hit testing or responder negotiation, so the theft is not reproducible off-device by any test written against this harness. The class-leak precondition IS testable (and now is); the responder theft is device-only.
- **Two siblings with the same shape, both currently callerless — check before you use them:** `ui/toggle.tsx` forwards one `className` into both its `TextClassContext` and its box, and `ui/badge.tsx` puts `active:opacity-80` on a plain `View` (the interop silently upgrades such a View to a Pressable, so it would eat taps inside a pressable row).
- **What not to do:** never pass a full button class string into a text/label class context — style the label with label classes. Don't trust a green mobile suite about anything styling-related while that stub is in place. And when a control is inert on device but fine in tests, suspect a child that has quietly become a touch responder before you suspect your handler.

**44. A receipt column on a compare-and-swap row needs its own updated_at trigger**
- **Symptom:** a parent taps Approve on a submitted week and the write fails, even though nobody else edited the hours. The nanny had just opened the same week (or the parent had, and the receipt stamped `parent_viewed_at`). The in-flight approve's compare-and-swap no longer matches.
- **Root cause:** `approveSubmittedWithEarnings` CAS-es on `(id, status, updated_at)`. The `timesheets` table used the shared `public.set_updated_at()` helper (`supabase/migrations/001_extensions_and_helpers.sql`), which sets `new.updated_at = now()` on **every** UPDATE. Sixteen tables use that function. A one-way `parent_viewed_at` stamp is an UPDATE that touches nothing else — but the shared trigger still bumps `updated_at`, so an approve that read the row before the stamp writes `.eq('updated_at', theEarlierValue)` and matches zero rows.
- **Where the fix lives:** `supabase/migrations/100_timesheet_parent_viewed.sql` gives `timesheets` its **own** trigger function `public.set_timesheets_updated_at()`. When the only changed column is `parent_viewed_at`, it preserves `OLD.updated_at`. Every other write — including a roll-up that rewrites identical values (`timesheetRepository.ts` around the `updated_at` bump the CAS relies on) — still sets `now()`. Pinned by `apps/api/tests/unit/migration100TimesheetParentViewed.test.ts` and `apps/api/tests/integration/timesheetParentViewed.integration.test.ts`.
- **What not to do:** never edit the shared `public.set_updated_at` (or migration 001) to special-case one column — that would change bump behaviour on every other table that uses it. Don't add a receipt stamp as a side-effect of GET. Don't bump `updated_at` from the repository on a viewed-only write and hope the trigger is "usually" skipped.

**46. A weekday holding TWO time blocks breaks materialisation three ways — and the worst one passes every test**
- **Symptom:** the parent's "usual week" gained multi-block days (Mon 07:00-13:00 **and** 15:00-17:00, migration 101). Three separate failures, in ascending order of how long they'd survive undetected: (a) the nightly horizon job 500s for every pattern behind the split one; (b) deleting the afternoon block leaves its shift on the family's calendar forever; (c) on a pattern accepted *before* the feature shipped, the second block is silently never created — not that run, not any future run — and the whole feature is dead for every existing household while looking fine for new ones.
- **Root cause (a) — the UID collision.** `shifts.ical_uid` is `text not null UNIQUE` **globally** (`015_shifts.sql:55`), and `deriveOccurrenceIcalUid` keyed it on `${patternUid}::${localDate}`. Two blocks on one Monday derive the *same* uid, so the batched `createMany` — one statement — aborts entirely and takes every other pattern's rows in that batch with it. Same blast pattern as #31: one loser kills the batch.
- **Root cause (b) — date-level orphaning.** `materialise` computed `producedDates = new Set(occurrences.map(o => o.localDate))` and orphaned any shift whose `local_date` wasn't in it. With two blocks per date, deleting one still leaves the date "produced", so the surviving-but-unwanted shift is never reconciled. Orphaning has to be "which *shifts* went unpaired", never "which *dates* went unproduced".
- **Root cause (c) — the legacy-UID guard over-matching, and why tests missed it.** Pre-existing shifts keep their 2-part uid forever (`ical_uid` is deliberately never re-keyed — #16, #29), so the `takenUids` guard that stops a *moved* shift being re-created must check the legacy form too. But the legacy scheme could only ever mint **one uid per date**. Check it for *every* occurrence and the second block on a date where a legacy shift already paired matches a uid that isn't its own, hits `continue`, and is never created. Every unit test passed: the fixtures were all new-world patterns, where no legacy uid exists to collide with. It was only found by reading the branch and asking "which occurrence does this uid actually belong to?"
- **Where the fix lives:** `apps/api/src/domains/schedule/services/scheduleMaterialisationService.ts`. `deriveOccurrenceIcalUid(patternUid, localDate, startTime?)` — 3-part when `startTime` is given, legacy 2-part when omitted. Pairing is now two passes over per-date buckets: pass 1 matches on the **exact instant** (the idempotent pass an unchanged nightly re-run takes), pass 2 hands an unmatched occurrence the first shift left in its date bucket (this is what preserves the old behaviour when a human *moved* a shift within its day — without it the shift is orphaned *and* duplicated, losing its id, its `ical_uid` and its change-request history). Orphans are whatever is left in the buckets. The legacy uid is consulted **only** for the earliest occurrence on its date. `recurrenceExpander.ts` carries `startTime` as wall-clock, verbatim, so the uid can't read differently across a DST boundary (#29).
- **What not to do:** don't key a uniqueness-bearing identifier on a granularity coarser than the thing it identifies — once a day can hold N blocks, anything keyed on `(pattern, date)` is a collision waiting for the second block. Don't let `NEVER_TOUCH_STATUSES` shifts stop consuming a bucket slot; they must still block re-creation on their date exactly as the old first-wins map did. Don't put an `await` inside the pairing loops — `scheduleMaterialisationBatching.test.ts` asserts identical repository-call counts for a 1-week and a 52-week horizon and is the #28 gate. And don't trust a green suite on a backward-compatibility branch whose fixtures contain no legacy data: the guard that only fires against old rows needs a fixture with old rows.

**45. Deleting a nanny's account must preserve her payroll history — four separate traps, each looked fine until traced end to end**
- **Symptom:** `DELETE /v1/users/me` for a carer left ghost `confirmed` shifts with a null carer materialising forever, those ghosts silently satisfying uncovered-care checks, a departed nanny's earnings vanishing from the year-end tax CSV, and — in a household later found memberless — the entire payroll record eligible for cascade deletion.
- **Root cause:** account deletion originally just deleted the auth user and NULLed `carer_id` (migration 033) without running any of the teardown `removeMember`/`leave` perform — no end-dating pay arrangements, no closing a running time entry, no terminating accepted patterns, no withdrawing change requests, no owner handover. That single gap fans out into four separate traps once you trace what reads `carer_id` downstream:
  1. **`earningsFor` vs `frozenEarningsFor` in the year-end tax CSV.** `apps/api/src/domains/timesheet/services/timesheetQueryService.ts`'s `exportYearEndSummaryCsv` skips rows with `if (!row.carer_id) continue;` — removing that skip is NOT enough, because the loop then calls `earningsFor`, which returns status `carer_removed` the instant `carer_id` is NULL, dropping the row one line later anyway. An APPROVED week has nothing left to resolve against a pay arrangement — the frozen snapshot IS the figure — so the fix is calling `frozenEarningsFor` instead, which prices correctly with no carer id. This CSV is the parent's Form 2441 / FSA handoff, so the failure mode is a nanny's earnings silently missing from a tax filing.
  2. **Bucketing carers on `carer_id` alone merges every departed carer under one heading.** `carer_id` stops being an identity the moment the account is deleted, so the bucket key must be `carer_id ?? household_member_id ?? carer_display_name`. That rule now lives in exactly one place server-side, `apps/api/src/domains/timesheet/utils/carerKey.ts`, mirroring `apps/mobile/src/domains/timesheet/utils/carerKey.ts` and the SQL in migrations `061_integrity_checks_departed_carers.sql` and `069_time_entry_void.sql`. Migration 058's `household_member_id` carries no foreign key precisely so it survives the membership row being cascade-deleted. Known limit, accepted: rows whose `carer_id` was already NULL before 058 ran have no membership to fall back to and still merge on a shared display name.
  3. **The reaper condition is zero ROWS in `household_members`, not zero ACTIVE rows.** `deleteIfMemberless` in `apps/api/src/domains/household/repositories/householdRepository.ts` — a nanny who merely left has `status='removed'` and still reads her pay history through `householdQueryService.listPastForUser()`, and a `candidate` row matters too. Counting only active rows would cascade-delete her entire payroll record — every `household_id` FK is `ON DELETE CASCADE` across 19 tables, so this is irreversible. The daily sweep (`apps/api/src/jobs/integrityCheckJob.ts`) additionally skips households younger than an hour, because `householdCommandService.create` inserts the household and its owner membership as separate statements, and the sweep could otherwise reap a household mid-creation.
  4. **Only six tables carry a `carer_display_name` snapshot** — `time_entries`, `timesheets`, `pay_arrangements`, `pto_ledger`, `expenses`, `terms_proposals`. `shifts`, `shift_events`, `handoff_notes`, `payments`, and `schedule_patterns` do NOT, which is why a departed carer's worked shift renders nameless while her timesheet still names her — check which side of that line a table falls on before assuming a name will be there.
- **Where the fix lives:** `DELETE /v1/users/me` now runs the same teardown `removeMember`/`leave` perform before deleting the auth user. `detectUncoveredCareForDate.ts` (`apps/api/src/domains/child/services/`) was additionally missing `carer_id` from its shift projection, so a carer-less `confirmed` shift silently counted as cover and suppressed uncovered-care alerts — it now projects `carer_id` and treats a null value as uncovered.
- **What not to do:** don't assume removing a `continue`-skip is a full fix without tracing what the very next line does with the now-null field. Don't bucket carer rows on `carer_id` alone anywhere new — use the shared `carerKey` helper. Don't extend the reaper's memberless check to "no active members" — it must stay "zero rows, any status." And don't assume every table that names a carer elsewhere also snapshots her display name — six tables do, the rest don't.

**16. `REVOKE ... FROM PUBLIC` must be explicit — `anon`/`authenticated` inherit from `PUBLIC` at creation time**
- **Symptom:** a `SECURITY DEFINER` RPC meant to be service-role-only turns out to be callable by an anonymous or logged-in client.
- **Root cause:** in Postgres, newly created functions are executable by `PUBLIC` by default, and both Supabase's `anon` and `authenticated` roles inherit from `PUBLIC` unless revoked — revoking only from `anon`/`authenticated` and forgetting `PUBLIC` itself leaves the hole open.
- **Where the fix lives:** every service-role-only RPC in this template's migrations revokes from all three explicitly, e.g. `supabase/migrations/006_subscriptions_usage_email.sql` (`process_subscription_event`, `check_and_increment_usage`, `increment_usage_counter`) and `supabase/migrations/007_pg_cron_vault_and_example_cron.sql` (`private.cron_api_base_url`, `private.cron_job_api_key`), each followed by `grant execute ... to service_role`.
- **What not to do:** when locking down a new RPC, don't stop at `revoke ... from anon, authenticated` — always include `PUBLIC` in the same statement (or a preceding one), and add the explicit `grant` to `service_role` so the intent is unambiguous.

**17. Play Store re-signs your app, so Google Sign-In needs the Play App Signing SHA-1 too, not just your local one**
- **Symptom:** native Google Sign-In works in every internal/debug build but fails (`DEVELOPER_ERROR` or similar) for real users who installed from the Play Store.
- **Root cause:** Google Play re-signs your app for distribution with its own "App Signing" key, whose SHA-1 fingerprint differs from your local debug/EAS build keystore — Google Sign-In's Android OAuth client is registered against a specific SHA-1, so only the fingerprint(s) you registered will authenticate successfully.
- **Where the fix lives:** this is a provisioning-process fix, not a code fix — see `PROVISIONING.md` §3, step 2: register **both** your build keystore's SHA-1 and the Play Console App Signing SHA-1 against the Android OAuth client.
- **What not to do:** don't register only the SHA-1 from your local/EAS keystore and assume it covers production Play Store installs.

**23. EventKit cannot see the Google Calendar *app* — only accounts in iOS Settings**
- **Symptom:** an iPhone user enables "Add my shifts to my calendar", picks what looks like a calendar, and events never appear in the Google Calendar app they actually use. Or the picker only offers "On My iPhone" and they think the feature is broken.
- **Root cause:** `expo-calendar` on iOS goes through EventKit, which only lists accounts configured under **Settings → Calendar → Accounts**. Installing the Google Calendar app alone does not add a Google source to EventKit. Events written to a local calendar stay on-device and never sync to Google.
- **Where the fix lives:** `CalendarPickerSheet` groups calendars by `source.name`, shows an honest empty state when no non-local writable calendar exists, and offers "Use On My iPhone / local anyway" only as a secondary action. Permission string + plugin live in `apps/mobile/app.config.ts` (`expo-calendar`). Sync is device-local marker-in-notes (`[steadily:<ical_uid>]`) — see `apps/mobile/src/domains/schedule/utils/calendarSync.ts`. Native module requires a new EAS build (not OTA).
- **What not to do:** don't silently default to a local calendar and call that success. Don't write device event ids into `calendar_event_links` (per-device ids; seam tables stay dormant for a future server OAuth path).

**23. Dev-only full-screen crash: "Couldn't find a navigation context" from a `Badge` (css-interop upgrade warning)**
- **Symptom:** on the first render pass of a fresh JS session (first tap into a tab, or a deep link), a screen dies to the full-screen error boundary with react-navigation's "Couldn't find a navigation context…", component stack pointing at an innocent component (`badge.tsx`). Self-heals on the next mount in the same session. Only in dev builds; production is unaffected.
- **Root cause:** two layers. (1) A native `active:` pseudo-class (e.g. `active:opacity-80`) on a plain, non-pressable `View` makes NativeWind/`react-native-css-interop` upgrade it View→Pressable; when the style registry isn't warm yet (fresh JS session), the upgrade lands *after* initial render, which triggers the library's dev-only `printUpgradeWarning`. (2) That warning's `stringify()` walks `originalProps` with recursive `Object.entries`, descending into React element children until it touches expo-router's vendored `NavigationStateContext` **default value — whose property getters all throw**. `Object.entries` invokes getters, so the diagnostic dump itself crashes the render.
- **Where the fix lives:** `patches/react-native-css-interop@0.2.6.patch` (via `bun patch`, wired in root `package.json` `patchedDependencies`) makes `stringify` walk `Object.keys` with per-property try/catch, degrading throwing getters to `"[Unserializable]"`; and `apps/mobile/src/components/ui/badge.tsx` dropped the `active:opacity-80` classes (a badge is not pressable — the class was shadcn boilerplate that only existed to trigger the upgrade).
- **What not to do:** don't chase the component named in the stack — the thrower is the css-interop interop wrapper, and the named component is just whoever mounted first with an upgrade pending. Don't put native `active:`/`hover:`/`focus:` pseudo-classes on non-pressable `View`s anywhere. And when a dev-only crash reproduces "only on first mount of a fresh session", suspect a warn-once diagnostic path before suspecting your own effects.

**43. A git worktree resolves `@steadily-nanny/shared-types` to the MAIN checkout, so shared-types edits silently do nothing**
- **Symptom:** you edit `packages/shared-types/src/...` inside a `git worktree`, and every consumer keeps seeing the old shape. Tests pass that should be red; `tsc` reports "has no exported member" for a symbol you just added. Two independent agents hit this on the same day.
- **Root cause:** a fresh worktree has no `node_modules`. Bun resolves by walking up the directory tree, and because worktrees created under `.claude/worktrees/` (or anywhere inside the repo) sit *below* the main checkout, the walk finds the main checkout's `node_modules/@steadily-nanny/shared-types` and stops there. You are editing one copy of the package and importing another.
- **Where the fix lives:** in the worktree, symlink it before doing anything else — `mkdir -p node_modules/@steadily-nanny && ln -s ../../packages/shared-types node_modules/@steadily-nanny/shared-types`. It is gitignored, so it never lands in a commit (`git ls-files node_modules` must stay empty).
- **What not to do:** don't conclude "the schema change had no effect" and start editing consumers to match the stale type. Don't `bun install` inside the worktree to fix it — that materialises a second full dependency tree per worktree. And when a worktree's test result contradicts the source you can read on screen, check module resolution *before* you doubt the test.

## Documented-only (v1 slim) — not shipped in this template

These fixes are real and were expensive to learn, but the feature they protect is intentionally **not** part of this template's v1 scope (see `PORTING.md` for the full exclusion list and why). The lesson is preserved here so it isn't lost; port the feature in from your reference app first, then re-apply the fix.

**18. Re-consent gate causing an infinite navigator remount loop**
- **Symptom (in a full implementation):** the app hangs on launch with a React "Maximum update depth exceeded" error, misleadingly pointing at an unrelated component.
- **Root cause:** a legal re-consent gate whose loading `enabled` flag was derived from the current route, combined with unmounting the navigator (`<Stack>`) during a *transient* loading state instead of only during a stable "blocked" state, created a mount → route-change → re-fetch → remount loop.
- **Not shipped:** this template has no legal/consent-gating subsystem in v1 (see `PORTING.md`). The lesson is preserved as an inline comment at the exact extension point: `apps/mobile/src/app/(private)/_layout.tsx` has a `RE-CONSENT GATE EXTENSION POINT` comment block stating the fix précis — keep the gate's `enabled` condition route-independent, and only unmount `<Stack>` for the stable blocked state, never a transient loading one (the same file already applies this same "keep `<Stack>` mounted, overlay a loader" pattern for its simple auth-session check, so the working example is right there to copy).
- **What not to do (when you build this):** don't derive a data-fetch's `enabled` condition from anything that changes on every navigation, and don't unmount your top-level `<Stack>` for any state you expect to resolve quickly.

**20. Legal policy publish step must run on every policy-version bump**
- **Symptom (in a full implementation):** sign-up starts failing with a 500 error referencing a missing "archived policy version."
- **Root cause:** a legal-publish pipeline that renders and archives policy documents by version can get out of sync if someone bumps the "current" policy version without re-running the publish/archive step for that version.
- **Not shipped:** the legal-publish pipeline is excluded from this template's v1 (see `PORTING.md`). The lesson: if you port this subsystem in, treat "bump the current version" and "publish/archive that version's rendered content" as one atomic operation, never two separate steps a person can forget to pair.
- **What not to do (when you build this):** don't allow a policy-version constant to be bumped in code without an automated check that a matching archived/rendered version exists.

**21. Day-since-X date math must use local timezone, not UTC**
- **Symptom (in a full implementation):** a "day 1" / "day since signup" feature is off by one for users, especially near midnight in their local timezone.
- **Root cause:** computing "today" or "days since X" using UTC-based date math instead of the user's local calendar day produces an off-by-one for a large fraction of the day depending on timezone offset.
- **Not shipped:** no shipped code path in this template currently computes a day-since/streak-style value (no such feature exists yet in the widget example). If you build one, compute "today" from local time, not `new Date().toISOString()` truncation, and write a unit test that pins a specific timezone rather than relying on the CI runner's default timezone.

**22. Teaching-copy `biome.json` breaks lint-staged as a "nested root config"**
- **Symptom:** `git commit` fails at the husky pre-commit hook with `× Found a nested root configuration, but there's already a root configuration.` — even though `bunx biome check .` from the root is green.
- **Root cause:** Biome 2.x treats ANY `biome.json` found while resolving config as a root configuration. The copy-paste teaching file `docs/templates/biome.json` conflicts with the real root config the moment lint-staged passes it (or any staged file near it) as an explicit path — explicit paths bypass the `docs/**` ignore, and config discovery errors before ignores are evaluated.
- **Where the fix lives:** root `package.json` `lint-staged` block — patterns are scoped to `{apps,packages,scripts}/**` plus root-level files, so docs are never passed to Biome (they're biome-ignored anyway).
- **What not to do:** don't "fix" this by deleting `docs/templates/biome.json` (it's the copy-paste reference for new repos) or by adding `root: false` to it (that would corrupt the teaching copy — it IS meant to be a root config in the repo that copies it).
- **Update (D16):** the lint-staged scoping above only ever covered the pre-commit-hook path. The plain root scripts — `bun run format` / `bun run format:check` (`biome check … .` / `biome format .` over the whole tree) — hit the exact same nested-root-config error directly, with no lint-staged file-scoping in front of them to save them, and `CLAUDE.md` instructs every contributor to run `bun run format` before committing. That command had never actually worked in this repo's history (see `docs/DEFECT-LOG.md` D16). Also verified directly: adding a `!docs/templates/**` negation to the root `biome.json`'s `files.includes` does **not** help — Biome's nested-root-config discovery runs before `includes`/ignores are evaluated, confirming the root-cause note above. The actual fix: the teaching file was renamed `docs/templates/biome.json.template` (content unchanged — still a valid root-shaped Biome config, still the copy-paste reference; only the filename changed so Biome's config-discovery, which keys off the literal name `biome.json`, never finds it in the first place). This is strictly more robust than the lint-staged scoping — it closes every invocation path, not just the pre-commit one — and doesn't violate either "what not to do" above.

**47. `hours_changed_after_payment_at` and the D46 drop/re-issue trap**
- **Symptom:** The API fails to route to an updated database function if the signature has changed.
- **Root cause:** The `record_timesheet_payment` signature was dropped then re-created instead of replacing in place, preventing overload matches. When a function signature changes, PostgREST will fail requests using the old argument list unless an overload is preserved or the client is updated first.
- **The fix:** Be careful with drop/re-issue; if a signature changes, ensure both API and DB are coordinated, or maintain an overload.

**48. The `net._http_response` vs `job_runs` monitoring distinction**
- **Symptom:** A cron job appears successful in `cron.job_run_details` but no work is done.
- **Root cause:** `cron.job_run_details.status = 'succeeded'` only proves that `pg_net` accepted the enqueue. The actual HTTP result lands in `net._http_response`. `job_runs` is the true signal of job success.
- **The fix:** Read `job_runs` for job outcomes; use `net._http_response` to catch jobs that fail to reach the API.

**49. The `ScheduleBuildScreen.tsx` overlap bug**
- **Symptom:** A week sent to the nanny invents hours the parent never asked for (e.g., merging 07:00-13:00 and 15:00-17:00 into a single 07:00-17:00 block).
- **Root cause:** `unique(pattern_id, weekday)` in the database collapsed independent blocks.
- **The fix:** Use `unique(pattern_id, weekday, start_time)` to allow disjoint windows to stay separate, and merge only touching/overlapping windows.

**50. Accepting a REVISED usual week 500s — supersede must run before the accept write**
- **Symptom:** the nanny taps Accept on a second (revised) usual week and gets a generic error. Log shows `DatabaseError: Failed to update schedule_patterns` from `schedulePatternCommandService.respond`. The FIRST usual week accepts fine; only a revision fails.
- **Root cause:** migration `104_schedule_invariants.sql` added `schedule_patterns_one_accepted_idx` — a unique index allowing exactly one `accepted` pattern per `(household_id, carer_id)`. `respond` wrote `status = 'accepted'` first and called `supersedePriorAccepted` afterwards, so the write collided with the prior accepted pattern still holding the slot. The 104 invariant was added long after `respond` was written; nothing re-checked the ordering.
- **Where the fix lives:** `apps/api/src/domains/schedule/services/schedulePatternCommandService.ts` — `supersedePriorAccepted(pattern, now)` now runs BEFORE the `patternRepo.update`. Ordering is pinned by a test in `tests/unit/domains/schedule/services/schedulePatternSupersede.test.ts`.
- **Also fixed:** `BaseRepository.update` swallowed the Postgres `message`/`code` (unlike `create`, which forwards both), so the log said only "Failed to update schedule_patterns" with no constraint name. It now forwards `details` and `code`.
- **What not to do:** don't add a uniqueness invariant in a migration without grepping every service path that writes the constrained column — a "single accepted row" index turns any update-then-clean-up sequence into a hard failure. And don't leave a repository error handler that drops the driver's message; the next 500 costs an hour of log archaeology.

**51. `className` size/weight overrides are DEAD on typography components — emphasis silently does nothing**
- **Symptom:** a developer writes `<Body className="text-sm text-muted-foreground">` or `<Body className="font-medium">` to make something smaller or bolder, and it renders at the token's own size and weight instead. No error, no lint warning, no failing test — the code reads correctly and the screen looks flat. It survives review because the intent is legible in the diff.
- **Root cause:** `createTypographyComponent` (`apps/mobile/src/components/ui/typography/factory.tsx`) emits `fontSize`, `lineHeight`, `fontWeight`, `fontFamily` and `letterSpacing` as an **inline `style`**, and an inline style always beats a NativeWind `className`. This is deliberate — it is what guarantees a token renders at its token size — but it means every `text-*` / `font-*` class on `H1…H4`, `Body`, `Small`, `Caption`, `Label`, `MetadataLabel`, `Figure*` is a no-op. The factory's own header comment says so, and `factory.test.tsx` locks it in ("className font-light is dead — token weight must still render").
- **Where the fix lives:** use the **`weight` prop** (`light|regular|medium|semibold|bold|extrabold`) for emphasis, and pick a different component for a different size. Fixed call sites: `apps/mobile/src/domains/pay/components/AmountRow.tsx` (dead `font-medium` on the VALUE of every money row in the app, so "Still to pay" and "£180.00" rendered identically), `apps/mobile/src/domains/today/components/ClockOutSheet.tsx` (dead `font-semibold` on the total being recorded), and eight sites in `apps/mobile/src/domains/today/components/TodayCoverage.tsx` where `<Body className="text-sm">` had been rendering at 16px, leaving the parent's most-read card with no secondary text rung at all.
- **What not to do:** don't reach for Tailwind to emphasise a typography component, and don't "fix" the factory to let className win — that would let any call site silently break the type ramp, which is the bug this design deliberately prevents. Note the asymmetry: on a **plain `<Text>`** (`apps/mobile/src/components/ui/text.tsx`) className sizing *does* work, because it sets no inline style — so the same class behaves differently on `<Text>` and on `<Body>`.

**52. `Figure` (16/400) and `Figure28` (28/700) are different components with near-identical names**
- **Symptom:** a number renders visibly smaller and lighter than the label sitting next to it. Concretely, `DayHeader` rendered a day's total hours in `Figure` (16/400) beside a `DayGroup` label (17/600) — so the number the header exists to state was smaller *and* two weight steps lighter than the word "Monday".
- **Root cause:** `Figure` is the body-sized tabular token for digit *columns*; `Figure28` is the card-level 28/700 number. The design docs say "Figure" for both, sometimes forty lines apart, so the ambiguity is baked into the spec as well as the code.
- **Where the fix lives:** `apps/mobile/src/components/ui/day-header.tsx` (the total now renders at its label's weight). When reading a spec line that says "Figure", check the size it quotes: 16/24 means `Figure`, 28/34 means `Figure28`.
- **What not to do:** don't assume "Figure" means the big one. If you are stating a card-level number — a week total, an amount, a headline figure — you want `Figure28`.
