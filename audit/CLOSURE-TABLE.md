# Closure Table — every confirmed defect and the test that proves it

Maps all 27 adversarially-confirmed findings from [`00-INDEX.md`](./00-INDEX.md) (22 entries; some are merged root causes citing several ids) to the code that fixes them and the tests that pin them.

**Method.** Test names are quoted **verbatim** from source. Line numbers are working-tree lines at the time of writing (nothing is committed yet — they will move). Where a finding was fixed in two rounds (an adversarial reviewer reopened it), both rounds' tests are listed. Paths are repo-relative.

**A passing test is not evidence of closure.** Every row below was checked by tracing the fix to the *trigger* stated in `00-INDEX.md`, not by observing a green suite. Two findings in this batch (F-B1-3, F-B2-4) passed their own round-2 tests while the original defect stayed reachable by a path no test covered — see [Round-3 reopens](#round-3-reopens). Where the trace is incomplete, the row says so.

**Result: 22 of 22 entries (all 27 ids) have at least one direct test. Zero `NO DIRECT TEST`.** Two carry a coverage caveat, flagged inline — see [Caveats on "direct"](#caveats-on-direct). One repository pair reachable from the F-B2-4 fix is untested — see [Known limitations shipped](#known-limitations-shipped) item 2.

Seven migrations now sit behind this work: `049`–`055`. Two landed after the first draft of this document and changed what it could claim — `054` scheduled a recovery job that had never actually run, and `055` gave `time_entries` its first database-level overlap backstop.

## Round-2 reopens

Seven findings were reopened by the adversarial reviewers after the first fix landed.

- **F-B2-4** — R1 added a clock-in guard (`timesheetCommandService.ts:361`), which stops the *stuck row* but not the *underlying conflict*: a paid cancellation recorded over a window she had already partly worked still double-banked those minutes (worked entry + full-span cancellation entry). R2 trims the cancellation entry to the remainder around real work (`:636-676`), returns `null` when she worked the whole window, and asserts `worked + cancellation == booked span` exactly.
- **F-B1-1 (`spansOverlap` running-entry arm)** — R1 replaced the week-filtered overlap query with a clock-instant one, so cross-Monday rows were finally visible. But `spansOverlap` still compared a running entry's `clock_out_at === null` as a zero-length instant, so a retroactive entry starting *after* a running session began saw no overlap and was accepted. R2 (`:235-236`) treats a null end as `[in, ∞)`. Without it, the carer-global `time_entries_one_running_per_carer` index would have locked her out of clock-in everywhere.
- **F-B4-2 (first marking outside the lock)** — R1 serialised only the *correction* path through `apply_pto_correction`; `markTimeOffPaid`'s first marking still wrote `usage` rows through `ptoRepo.create` in a per-day loop, outside the lock, relying on 045's per-day unique index. A rival marking committing mid-loop could leave a total neither parent asked for. R2 routes the first marking through the same locked batch (`ptoCommandService.ts:322-338`), deciding `usage` vs `adjustment` per day *inside* the batch the CAS vouches for (`:411-419`), with `kind` added to 050's recordset (`050:129`). `ptoRepo.create` now has zero callers in `ptoCommandService`.
- **F-B4-3 (burned invite)** — R1's CAS claim made redemption single-use, but claimed *before* `createMembership`; any failure there (transient DB error, or the unique-constraint hit when a previously-removed member retries) consumed the code permanently with no membership to show for it. - **F-B4-8 (unbounded duplicate-apply)** — R1 sent a failed apply back to `pending` for a re-drive, which by itself was an unbounded loop: every expiry sweep would re-run an applier that had already half-committed. R2 bounded it at `MAX_APPLY_ATTEMPTS = 2` with a forward-pushed `timeout_at` (so the on-read expiry cannot re-fire immediately) and a terminal `withdrawn` with the error in `payload`, plus duplicate suppression in `insertExtraShift` (`:576-584`) keyed on the natural key rather than the approval id — which also covers the ungated `createExtraShift` double-tap an approval-id key would have missed.
- **F-B2-5 (no retry path existed)** — R1 stopped swallowing the recorder error, so accept now 500s instead of returning 200 with no payable row. R2 added `cancellationPayReconcileJob.ts` + `listCancellationPaidSince`, sweeping 30 days and re-calling the idempotent recorder, counting approved-week blocks separately as needs-a-human.
- **F-B3b-1 (`carer_id` sibling-column bypass)** — R1 removed `status` from `UpdateSchedulePatternSchema` and whitelisted forwarded fields, closing the direct force-accept. ## The money ruling: household-scoped subtraction, carer-global overlap

A product decision made during the fix work, not a defect, but it sets the semantics every cancellation test now asserts against. **When household A cancels with pay and the carer works for household B inside that window, A owes the full booked window.** Compensation for time deliberately *not* worked does not occupy the clock, so B's hours do not reduce A's bill.

That splits one question into two scopes, and the split is the whole design:

- **Subtraction is household-scoped** — `timesheetCommandService.ts:671`, `alreadyBooked.filter(row => row.household_id === shift.household_id)`. Only this household's rows trim this household's remainder.
- **The overlap check stays carer-global** — `assertNoOverlap:1003`, `if (other.kind !== 'worked' && other.household_id !== householdId) continue;`. She still cannot be in two places at once.

The decision comment at `:994-1002` is the authority, not this document: *"Every caller writes WORKED time, so two clauses decide it: other is worked -> refuse, she cannot be in two places at once; same household -> refuse, that is the within-household double-bank … Anything else is another household's `cancellation_paid`, which is compensation for time deliberately NOT worked and therefore does not occupy the clock. She may work for B inside a window A is paying her to have free."*

Migration `055` reproduces the same table in the schema, and its contract test names the cases outright: `PERMITS: worked h1 vs cancellation h2 — THE £120 CASE`; `REFUSES: worked h1 vs worked h2 — cannot be in two places`; `REFUSES: worked h1 vs cancellation h1 — same window paid twice`; `PERMITS: cancellation h1 vs cancellation h2 — both owe`; `REFUSES: cancellation h1 vs cancellation h1 — one family, twice`; `REFUSES: adjustment h1 vs worked h2 — relabelled presence`. **One row of that table diverges between app and schema — see [Known limitations shipped](#known-limitations-shipped) item 1.**

## Known limitations shipped

Deliberate ceilings, each stated in code at the point it bites — except item 1, which is not deliberate.

1. **The app check and the DB constraint disagree on one row of the permission table.** Not a stated ceiling; a divergence found while verifying `055`, reported here because it is the one place the two authorities on the money rule contradict each other.
   `055`'s carer-global constraint keys on `kind <> 'cancellation_paid'`, and its header argues at length that this is correct because a `manual_adjustment` **is** worked time — presence relabelled. But `assertNoOverlap:1003` keys on `other.kind !== 'worked'`, which is the exact hole `055` says must not exist. A `manual_adjustment` in household B plus a new `worked` entry in household A passes the app check and then hits a raw `23P01` from Postgres instead of a typed `TimeEntryOverlapError`.
   **Latent today:** no code path writes `kind: 'manual_adjustment'` — the literal appears in `apps/api/src` only in comments and in `earningsService`'s summing, though `017_time_tracking.sql:32-33` permits it. The moment that escape hatch ships, this diverges for real, and the user-visible symptom is a 500 rather than a clean refusal.
   Two narrower, deliberate divergences sit alongside it: the DB is **looser on running entries** (both constraints are partial on `clock_out_at is not null`, so the schema permits a completed span overlapping an open session while the app forbids it — documented at `055:60-73` with its own `ponytail:` note), and the app is **stricter when the row being edited is itself `cancellation_paid`** (`assertNoOverlap` hard-codes the prospective row as worked, so `updateEntry` on a cancellation fragment is refused where `055` would permit it). Both are safe directions; the `manual_adjustment` one is not.
2. **~~Fragmented cancellation remainder is refused outright.~~ LIFTED — 053 has landed end to end.** This was the headline ceiling when the fix work started: worked time in the *middle* of a cancelled window leaves two disjoint remainders, `039_cancellation_paid_unique.sql`'s one-row-per-shift index made that shape unrepresentable, and `recordCancellationPaidEntry` threw `CANCELLATION_REMAINDER_FRAGMENTED` rather than pay one fragment and silently underpay the other.
   It is now closed on both sides. `053_cancellation_paid_split_remainder.sql` swaps the shift-scoped index for `time_entries_one_cancellation_paid_per_span` on `(shift_id, clock_in_at) nulls not distinct` (contract test `migration053CancellationPaidSplitRemainder.test.ts`, 22 pass), **and the app side is wired**: `recordCancellationPaidEntry` returns `TimeEntry[]` and writes one row per remainder (`timesheetCommandService.ts:639-673`), `writeCancellationFragment:685` recovers a lost 23505 span-scoped rather than shift-wide, `findCancellationPaidForSpan:173` is the new span lookup, and `findCancellationPaidForShift:143` gained the `.limit(1)` that keeps `.maybeSingle()` from erroring on a legitimately multi-row shift. No `CANCELLATION_REMAINDER_FRAGMENTED` remains in the codebase.
   **Residual ceilings, both stated in code.** `timeEntryRepository.ts:138-141`: *"ponytail: answers "at least one exists", not "all fragments exist" — a partially written split still reads as settled here. Callers that must distinguish should re-run `recordCancellationPaidEntry`, which is self-healing and writes only what is missing."* That caller is `cancellationPayReconcileJob.ts:89`, which uses exactly this method — so **a half-written split is invisible to the reconcile sweep**. The self-healing property it relies on is tested (`writes only the MISSING fragment after a partial failure — retry is safe`); the sweep noticing that it needs to run is not.
   **And a test gap:** neither `findCancellationPaidForShift` nor `findCancellationPaidForSpan` has a repository-level test — both appear in `apps/api/tests/` only as service-test mocks. The `.limit(1)` the code itself calls *"load-bearing since migration 053"* is therefore unexercised; a regression removing it would pass the whole suite and fail on the first split shift in production.
3. **A crash between the invite claim and the membership insert still strands the code.** The R2 fix is compensation in a `catch`, so a process death skips it. `householdCommandService.ts:223-225`: *"ponytail: compensation only, so a process that dies between the claim and the insert still strands the code. A claim-expiry sweep would close that; not worth it until it happens."*
4. **A hard process kill between reminder claim and send is still a missed reminder.** Explicitly the chosen side to fail on. `reminderJob.ts:22-28`: *"a hard process kill inside that narrow window is unrecoverable without a two-phase (reserve/confirm) ledger, which would need a schema change this job doesn't have. Given the choice, that's the right side to fail on: an occasional duplicate reminder from an overlapping-run race is a minor annoyance, a permanently swallowed one (the bug this replaced) is a missed shift or an unpaid timesheet nobody finds out about."* Release is also best-effort — `reminderLogRepository.ts:60-64` notes a failed delete leaves that slot claimed until cleaned up out of band.
5. **The partially-applied approval ceiling — corrected.** The brief described this as *"a partially-successful approval applier can still create one duplicate on its single retry."* **That is not what shipped.** All three registered appliers are duplicate-safe on a sequential retry: `extra_shift` early-returns the existing shift (`shiftChangeRequestCommandService.ts:582-584`, asserted by `does not create a second extra shift when a retried approval re-runs after a partial failure`), and `cancel` / `short_notice_change` go through the single `openWithSupersede` RPC, which supersedes every other pending request on the shift in one statement. The four real residual ceilings are:
   - **Partial work is not repaired.** `insertExtraShift` returns `existing` *before* `insertChildren` and the `extra_shift_proposed` event. If attempt 1 died between the shift insert and those, the retry is a no-op returning a shift with **no child-coverage rows and no audit event** — not a duplicate, an incomplete shift no further retry will finish.
   - **Cancelled-in-between.** The guard excludes `status = 'cancelled'` (`shiftRepository.ts:298`, deliberate per `:276-277`). If the partial shift is cancelled before the retry, the retry *does* create a second shift.
   - **Check-then-act concurrency.** `shiftRepository.ts:279-283`: *"ponytail: check-then-act, so two SIMULTANEOUS creates can still both miss. The retry path this guards is sequential (a bounded re-drive after a failure), so that race is not the failure mode in play. A partial unique index on `(household_id, carer_id, starts_at, ends_at) where kind = 'extra' and status <> 'cancelled'` is the real fix — it needs a migration."*
   - **Terminal give-up is log-only.** After two attempts the approval becomes `withdrawn` with `apply_error` in `payload` and a `logger.error` (`approvalApplierRegistry.ts:125-134`). Nothing notifies the requester. Also `coParentApprovalRepository.ts:99-102`: *"ponytail: the attempt count and error live in the existing `payload` jsonb … real columns would need a migration. Its remaining ceilings are real but smaller: one existence query per candidate (`:86-88`, with a `ponytail:` naming the batched-`in` upgrade), and approved-week blocks counted as needs-a-human rather than repaired (`:100-113`). 11. **`insertExtraShift` dedupe is an existence check, not a constraint** — a narrowed window, not a closed one. Confirmed still check-then-act: no migration through `055` adds a partial unique index for extra shifts (the only shift-adjacent unique indexes are `039` on `time_entries` and `025` on `shift_events`). One limitation was reported to me for inclusion and I could not substantiate it, so it is not listed above.

- **"±1 minute rounding drift on a middle-split cancellation (~£0.25/shift), deliberately not chased."** No such statement exists anywhere in the codebase. Searched `apps/api/src`, `apps/api/tests`, `docs/` and `supabase/migrations/` for `rounding`, `drift`, `0.25`, `one minute`, `middle-split`, `not chased`, `deliberately not`. ## Product gaps surfaced

Not defects — missing product surface that the fix work made visible.

1. **There is no way to remove a household member.** `HOUSEHOLD_MEMBER_STATUSES.REMOVED` exists (`packages/shared-types/src/schemas/household.schema.ts:56`) and is read all over — but **nothing writes it**. `householdMemberRepository.ts` never sets `status` (its only four references are `.eq('status', 'active')` filters at `:32`, `:51`, `:74`, `:93`), no service method transitions a membership, and `householdRoutes.ts` exposes no removal endpoint. Every removed-carer guard shipped in this pass — F-B3b-3's `findActiveMembership` in `getOwnedTimeEntry` and `loadOwnedPending`, `timesheetQueryService.ts:214`'s `CARER_REMOVED` hours-only fallback, the role check in `schedulePatternCommandService.respond` — is therefore **currently unreachable except by a manual DB edit**. The guards are correct and tested; they simply have no product path that triggers them yet.
2. **A previously-removed member cannot rejoin.** Reactivation is unimplemented: `createMembership` always inserts, so a removed member who redeems a fresh invite hits the `(user_id, household_id)` unique constraint. The invite fix handles this gracefully — the claim is released rather than burned, and `releases the claim for the removed-member case too, where createMembership hits the unique constraint` pins it — but the *user* still cannot rejoin. Closing gap 1 without closing this one would make removal irreversible.
3. **The Today card has no answer for two carers on the clock at once.** `NannyLiveStatusCard.tsx:105` uses `.find(e => e.status === 'running')` — whichever running entry the API returns first, with no sort and no tie-break. The card renders that one carer's name and clock-in time; **the second running carer is not surfaced at all** — no name, no count, no "and 1 other". This is silent omission, not a wrong number (the running arm sums nothing), and it is untouched by the F-B1-3-sibling fix, which only corrected the *finished* arm. A product decision is needed: name both, name one and count the rest, or stack a card per carer.

## Review rounds (round 2)

Four of the rows above went through adversarial re-review after they were green. What each round caught is the substance of this section — three of the four findings were **money defects created by the fix itself**, and one was a fix that did nothing at all.

**Money core — four rounds.** Lane B ran B1 (formula promotion) → C7 (round-once residual) → C6 (Monday split) → NEW-9 → NEW-10.

- **CRIT-1 — the adoption path was dead code.** `findAbandonedFragment` compared timestamp *strings*: PostgREST returns `+00:00`, our own writes are `.000Z`. Same instant, different string, so it matched nothing, ever. Every retried clock-out re-split the session, hit the overlap guard, and left the carer **permanently unable to clock out** — the exact F-B2-4 stranding class this audit exists to remove. Fixed at `:795` (instant compare) and pinned by `adopts an orphan written with our own .000Z formatting too`, a test that exists because the first version used only PostgREST-shaped fixtures and passed against the broken code. Now `GOLDEN-FIXES.md` #25.
- **CRIT-2 — cancellation pay was not split, and the guard loop was dead.** C6 split *worked* sessions at Monday midnight but left cancelled windows whole, so a cancellation crossing Monday wrote one row into one week while the approved-week guard iterated a collection that could only ever hold one entry. A fragment could land on an already-approved week — the same class as *Beyond the original 27* item 10, recreated. Fixed by `splitAtWeekBoundaries` (`:341-361`, called `:983`); pinned by `REFUSES when the MONDAY week is already approved`.
- **NEW-9 — a freed sliver inherited the whole gap's share: ~240 minutes, about £60 overpay.** Reachable through an ordinary carer correction followed by the nightly reconcile — not an exotic path. Pinned by `pays only what the gap has left when part of it is already banked`.
- **NEW-10 — the containment predicate was lost, underpaying 240 minutes.** Back-to-back cancelled shifts: a fragment belonging to the *neighbouring* window was counted as already-banked against this one. Fixed by the instant-compared containment test at `:1077-1078`; pinned by the `a neighbouring window is not this window (NEW-10)` block.

All four were fixed and re-verified; final reviewer verdict CLOSED.

**C1 — one round, an S0.** The identity work was correct in the data layer and wrong on screen: the week header and the approve dialog named the **live** nanny above a *departed* carer's total. A parent would have approved one carer's money under another's name. Fixed by deriving `entryCarerIds` from the selected tab rather than the household member list; `NannyLiveStatusCard`'s `"Someone"` placeholder became the snapshot name in the same pass. Mixed-vintage over-splitting was investigated and proven **unreachable** — 058's backfill is all-or-nothing per carer.

**C2 — one round, and it would have shipped a security regression.** See `RESIDUAL-RISK.md` §4: round 1's release CAS could free a **fresh** claim by the same user, resurrecting single-use invite codes — worse than the burned code it was fixing.

## Review rounds (round 3)

Seven fixes were reopened after being written, reviewed and green. Listed because the substance of this section is what a green fix can still be:

- **An env var crashing boot on an empty string.** `.optional()` treats `''` as present-and-too-short, so a verbatim copy of `.env.example` refused to start. The fix is a `'' → undefined` preprocess, and the reason it needed a second reader is that the test fixture omitted the key entirely rather than setting it empty — the test proved the code agreed with the test.
- **Capped inputs multiplying into uncapped money.** The specification capped every input field; the figure that reaches a payslip is the product. Closing only what was specified would have left a five-line fix that looked complete and bounded nothing that matters.
- **A stale Sentry identity after a failed signOut.** The clear was on the success path. supabase-js can resolve a signOut *error* without emitting `SIGNED_OUT`, which leaves the previous user's id attached to the next session's crashes — so the clear moved into a `finally`, and the test that pins it is the non-4xx-error one.
- **An inert fix built on a false database premise.** The coverage-gap work was written as though `ignoreDuplicates` had suppressed the conflict. It had not, because the index is an expression index — so the "fix" filtered rows from a batch that had already thrown. Same family as `cancellationPayReconcileJob` never being scheduled: code that passed its tests and did nothing.
- **A 404 leaking existence** on one of the new read gates — the wrong error for an unknown household, in a place where "missing" and "not yours" must be indistinguishable.
- **Rejoin resurrecting money state.** The first cut reactivated a membership and left the old pay arrangement live, so a returning carer silently kept terms both parties had ended. That is what `065` exists to prevent, and it was found by asking what a rejoin *inherits* rather than what it changes.
- **20 fixtures broken by a schema change**, surfaced by the suite rather than the author — the healthy case, and the reason the previous six are worth writing down.

**And one instruction refused outright.** The specified PTO "stacking" fix addressed a bug that does not exist — balances are year-scoped — and would have denied a January rejoiner her annual grant. The implementer said so instead of building it. Fourth correction of the reviewer in this effort, and all four came from the implementer. Full account in `RESIDUAL-RISK.md` §4.

#### Then the review of fix 2 found the fix was dead code

Adversarial review of the past-households fix established that `isPastMember` was
**permanently false**: it derived from `GET /v1/users/me/memberships`, which filtered to
active rows, so nothing could ever set the flag and the removed nanny was still routed into
the signup wizard. **Its tests passed by mocking a payload the server could not emit.** Same
family as `findAbandonedFragment`'s string compare (round 2, `GOLDEN-FIXES.md` #25) and the
coverage-gap `ignoreDuplicates` premise (round 3, #31) — the test and the code shared an
assumption about a payload neither had seen.

The same review found something the device pass had not thought to look for: **time-off
create, cancel and update had no membership gate at all.** A removed member got 201, and
cancel appended adjustment rows to a past household's `pto_ledger` — **a money write by a
non-member.** All three now route through `assertActiveMember`
(`timeOffCommandService.ts:85`, `:136`, `:175`; the assertion at `timeOffQueryService.ts:91`),
pinned by `refuses a create from a caller with no active membership, and writes nothing`,
**`refuses a cancel from a caller with no active membership and attempts NO pto_ledger
write`**, `refuses an update from a caller with no active membership`, and the two
counterparts that keep the happy path honest — `leaves an ACTIVE member able to create` and
`leaves an ACTIVE member able to cancel, reconcile included`. The gate is deliberately
"holds **any** active membership" rather than "active here", because `carer_time_off` has no
`household_id`; the reasoning and its two consequences are ceiling **C37**.

#### The lesson, stated plainly

Round 2 established that **each new evidence class finds defects the previous one could not
see**. This pass is the sharpest instance of it in the whole effort, and it goes one step
further than the earlier statement: the unit suite missed what the API run caught, the API
run missed what the screen showed, and **the screen missed what a review of its own fix
caught.** Three of the four device-pass defects were invisible to every test in this repo —
one structurally so, by a stub in `bun.setup.ts` — and the fourth's fix was dead code whose
tests passed against a payload the server cannot produce.

Neither instrument dominates the other. A device pass cannot read a filter in a repository
method; a review cannot see an inert button. What closed this round was running both, in
that order, and letting the second one audit the first.
