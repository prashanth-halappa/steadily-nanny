### F-B7-3 | S2 | confidence: med
**Claim:** Several range-query and shift-write schemas validate ISO datetimes with lexicographic `>` instead of instant comparison; `CreateCarerTimeOffSchema` documents why that is wrong, but `CreateExtraShiftSchema`, `ShiftRangeQuerySchema`, and `MeShiftRangeQuerySchema` still use string compare.
**Location:** `packages/shared-types/src/schemas/availability.schema.ts:141-145` (correct `Date.parse` pattern), `apps/api/src/domains/shift/schemas.ts:75-77,112-124`, `apps/api/src/domains/me/schemas.ts:28-35`, `apps/mobile/src/api/endpoints/changeRequests.ts:55-68` (mirrors `CreateExtraShiftSchema`)
**Trace:** `validate(ShiftRangeQuerySchema|MeShiftRangeQuerySchema|CreateExtraShiftSchema)` → `shiftRepository.findByHouseholdAndRange` / `insertExtraShift` (no `Date.parse` guard in `shiftChangeRequestCommandService.ts:564-581`; DB `shifts_time_order` at `supabase/migrations/015_shifts.sql:60` is the backstop for writes).
**Wrong-number scenario:** `starts_at: "2026-08-05T22:00:00-08:00"` and `ends_at: "2026-08-06T05:00:00+00:00"` — ends is one hour before starts in absolute time, but `"2026-08-06" > "2026-08-05"` so Zod accepts. Extra-shift create then hits DB CHECK (500), or an inverted `from`/`to` query pair passes Zod and returns an empty overlap set (`shiftRepository.ts:141-142`), hiding shifts on the calendar. Unlikely with a single well-formed client, but produces wrong schedule visibility or a failed write, not a silently wrong paid total.
**Fix sketch:** Replace `.refine(data => data.ends_at > data.starts_at)` with `Date.parse(data.ends_at) > Date.parse(data.starts_at)` (and the same for `to`/`from` on range queries), matching `CreateCarerTimeOffSchema`.
