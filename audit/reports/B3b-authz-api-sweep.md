### F-B3b-1 | S0 | confidence: high
**Claim:** `PATCH /api/v1/schedule-patterns/:patternId` mass-assigns `status` (and `carer_id`) from the client body, so a parent can mark a draft `accepted` without carer consent and then materialise confirmed paid shifts.
**Location:** `packages/shared-types/src/schemas/schedule.schema.ts:100-103`; `apps/api/src/domains/schedule/services/schedulePatternCommandService.ts:138-146`; `apps/api/src/domains/schedule/controllers/schedulePatternController.ts:66-73`; `apps/api/src/domains/schedule/routes/schedulePatternRoutes.ts:44-48`; materialisation writes `status: 'confirmed'` at `apps/api/src/domains/schedule/services/scheduleMaterialisationService.ts:191-199`; `create` alone runs `assertCarerRole` at `schedulePatternCommandService.ts:115-116` (update does not).
**Trace:** Route validates `UpdateSchedulePatternSchema` (allows any `SCHEDULE_PATTERN_STATUSES` + optional `carer_id`) → `SchedulePatternController.update` passes `req.body` → `schedulePatternCommandService.update` only checks the row is currently `draft` then `patternRepo.update(patternId, input)` (full body). Parent then `POST .../amend` (`schedulePatternCommandService.ts:237-276`) or the schedule-horizon job calls `materialiseForHorizon`, which inserts shifts as `confirmed` without a carer `respond`.
**Wrong-number scenario:** Parent builds a draft with days + `carer_id` = nanny, `PATCH { "status": "accepted" }`, then amends or waits for horizon. Confirmed shifts appear with no nanny accept; short-notice cancel / clock-in match / cancellation-paid paths can then create or price `time_entries` the carer never agreed to.
**Fix sketch:** Drop `status` from `UpdateSchedulePatternSchema`; on update, whitelist fields and call `assertCarerRole` when `carer_id` is present (same as `create`).

### F-B3b-2 | S0 | confidence: high
**Claim:** Invite redeem is check-then-act with no conditional claim on `status = 'pending'`, so two different users can both join on one code under concurrency.
**Location:** `apps/api/src/domains/household/services/householdCommandService.ts:131-170`; `apps/api/src/domains/household/repositories/householdInviteRepository.ts:19-35`; `apps/api/src/shared/repositories/baseRepository.ts:74-78`; unique index only on `(user_id, household_id)` at `supabase/migrations/009_households.sql:100-101` / `112-124` (no single-redeemer claim).
**Trace:** `POST /households/invites/redeem` → `redeemInvite` loads invite by code, allows if not revoked/accepted and not past `expires_at`, then `createMembership` then unconditional `inviteRepo.update` to `accepted`. Concurrent double-redeem for the *same* user is translated via unique violation (`householdMemberRepository.ts:113-124`); two *different* users both pass the status read and both insert memberships.
**Wrong-number scenario:** Parent shares one nanny invite code. Alice and Bob redeem in the same window; both become active `nanny` members of household H. Either can clock in / submit hours / claim expenses against H’s pay arrangements.
**Fix sketch:** Claim with `UPDATE household_invites SET status = 'accepted', … WHERE id = $1 AND status = 'pending' RETURNING *` (0 rows → already used), then create membership; or serialize redeem in a single RPC/transaction.

### F-B3b-3 | S0 | confidence: high
**Claim:** Time-entry and pending-expense writes authorize by `carer_id === caller` only, not active household membership, so a removed nanny can still mutate hours and claim amounts.
**Location:** `apps/api/src/domains/timesheet/services/timesheetQueryService.ts:71-79` (`getOwnedTimeEntry`); call sites `timesheetCommandService.ts:326` (`clockOut`), `:590` (`updateEntry`); `apps/api/src/domains/pay/services/expenseCommandService.ts:426-439` (`loadOwnedPending`) used by `update`/`withdraw` at `:228-280`. Contrast: clock-in/retroactive and timesheet reads *do* use `findActiveMembership` (`timesheetCommandService.ts:250-256`, `timesheetQueryService.ts:221-227`). Membership removal is writable via RLS `"Parents can manage members"` (`supabase/migrations/009_households.sql:268-271`) updating `status` to `removed` (`:87`).
**Trace:** Parent sets nanny membership `status = 'removed'` (PostgREST or any writer). Nanny JWT still calls `PATCH /time-entries/:id` or `POST .../clock-out` → ownership middleware/`getOwnedTimeEntry` succeeds on `carer_id` alone → `rollUpIntoTimesheet` changes `timesheets.total_minutes`. Same for `PATCH/DELETE /expenses/:expenseId` via `loadOwnedPending`.
**Wrong-number scenario:** Nanny removed Monday; she `PATCH`es Tuesday’s submitted entry to add two hours (or inflates a pending expense `amount_minor`). Week totals / reimbursements change for a household she no longer belongs to; parent may later approve that figure.
**Fix sketch:** In `getOwnedTimeEntry` and `loadOwnedPending`, require `findActiveMembership(entry.household_id, callerId)` (same collapse-to-404 as timesheet `loadOwnedRow`).
