### F-B3-1 | S0 | confidence: high
**Claim:** Any active owner/parent can change a nanny’s `household_members.role` through PostgREST, and every API parent gate trusts that column — so a nanny can be escalated to `parent` and then approve her own timesheet (freezing `gross_minor`).
**Location:** `supabase/migrations/009_households.sql:268-271`; `supabase/migrations/040_rls_semantic_predicates.sql:132-135`; `apps/api/src/domains/household/repositories/householdMemberRepository.ts:23-33`; `apps/api/src/domains/timesheet/services/timesheetCommandService.ts:807-821,1266-1279`; `apps/mobile/src/lib/supabase.ts:14-15`
**Trace:** RLS policy `"Parents can manage members"` grants authenticated parents `UPDATE` on `household_members` with no column restriction (`009:268-271`, reproduced in `040:132-135`). The mobile app ships the Supabase anon key (`apps/mobile/src/lib/supabase.ts:14-15`), so a parent JWT can call PostgREST directly. `HouseholdMemberRepository.findActiveMembership` reads `role` from that table via service role (`householdMemberRepository.ts:23-33`). `timesheetCommandService.approve` calls `assertWriteMember`, which allows only `owner`/`parent` (`timesheetCommandService.ts:1266-1279`) then freezes earnings (`timesheetCommandService.ts:807-821`). There is no API route that updates `household_members`; role changes are not supposed to be client-writable (`grep` shows no `memberRepo.update` in `apps/api/src`).
**Wrong-number scenario:** (1) Parent JWT: `PATCH https://<project>.supabase.co/rest/v1/household_members?household_id=eq.<H>&user_id=eq.<nanny_uuid>` with body `{"role":"parent"}` (apikey = anon key, `Authorization: Bearer <parent_jwt>`). (2) Nanny JWT: `POST /api/v1/timesheets/<submitted_timesheet_id>/approve` with no body. Nanny passes `assertWriteMember`; `approveSubmittedWithEarnings` snapshots `gross_minor`/`earnings` for a week the carer approved herself — parent-only approval is bypassed and frozen pay is wrong-by-process (carer signed off own pay).
**Fix sketch:** Drop the authenticated `UPDATE` policy on `household_members` (membership/role changes service-role only), or add a `BEFORE UPDATE` trigger that rejects `role`/`status` changes unless `current_setting('role') = 'service_role'`.

### F-B3-2 | S1 | confidence: med
**Claim:** Parents can mutate `shifts` (and related schedule rows) directly via PostgREST, bypassing co-parent approval gates and the audited RPC paths the API uses for the same mutations.
**Location:** `supabase/migrations/015_shifts.sql:226-229`; `supabase/migrations/014_schedule_patterns.sql:142-152`; `apps/api/src/domains/shift/services/shiftChangeRequestCommandService.ts:336-366`; `apps/api/src/domains/shift/services/shiftCommandService.ts:169-179`; `apps/api/src/domains/household/services/approvalGateService.ts` (gate never runs on direct SQL)
**Trace:** RLS `"Parents can write shifts"` is `FOR ALL` for `is_household_parent(household_id)` (`015:226-229`); same pattern for `schedule_patterns` insert/update/delete (`014:142-152`). API short-notice cancel/time-change routes through `approvalGateService.assertApprovalAllows` (`shiftChangeRequestCommandService.ts:336-366`); parent edits go through `ShiftRepository.applyParentEdit` RPC with day-thread events (`shiftCommandService.ts:169-179`). A parent JWT + anon key can `PATCH`/`INSERT`/`DELETE` on `shifts` (and patterns) without hitting either path. Money tables (`timesheets`, `time_entries`, `pay_arrangements`, `expenses`, `pto_ledger`) correctly have SELECT-only RLS for clients (`017:133-145`, `041:193-197`, `044:157-161`, `043:175-177`).
**Wrong-number scenario:** Household has `approval_mode` requiring co-parent sign-off. Parent B uses PostgREST: `PATCH .../shifts?id=eq.<shift_id>` with `{"status":"cancelled","cancellation_paid":true,"cancelled_at":"..."}` while co-parent A never sees an approval row. That does not auto-create a `cancellation_paid` time entry (only `shiftChangeRequestCommandService` → `recordCancellationPaidEntry` does), so it may not immediately freeze wrong cents — but it can strand schedule state (cancelled shift, no change-request audit, co-parent gate skipped) and block the normal paid-cancel path that would create the correct `time_entries` row and roll-up.
**Fix sketch:** Narrow parent RLS on `shifts`/`schedule_patterns` to `SELECT` only (same as money tables); keep all writes on service role + API command services.
